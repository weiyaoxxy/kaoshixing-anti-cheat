# 深度复核与审阅问题

复核日期：2026-11-01。范围为已归档的 Apple 文档、本机 macOS 26.5 SDK，以及此前 macOS 26.6.2（25G83）PoC 的证据。本文是本轮新增文档，不覆盖此前交付。文中 `[Dxx]` 对应末尾参考文献与 `research/deep-review-20261101/` 的原始快照。

## 可供评审采用的结论

1. `NSWindow.sharingType = .none` 的本机有效现象与 Apple 不推荐将其作为防捕获机制应同时保留。官方资料足以解释两者并非可靠性承诺上的冲突，但**没有解释本机具体是哪条 WindowServer 内部路径保留了此行为**，不能自行补出原因。
2. Clear Key 实验并非必须等待 FairPlay 生产资格。Apple 公开支持明文密钥交付，并有将测试流配置为 `SAMPLE-AES + KEYFORMAT=identity` 的方法。本轮已用合成录制与 Bento4 生成真正的 SAMPLE-AES 测试素材，完成离线解密正对照，并完成原生 AVPlayer 三组及两组初始化对照：加密 false 的外部图隐藏、true 可见；但 false 的同进程 VideoOutput 仍有明文，必须注明与文档描述的实测差异。它与“把普通视频加密成整段 AES-128”是不同测试。[D04–D08、D24]
3. AutomaticAssessmentConfiguration（下称 AAC）是考试场景可正式申请的公开方案；它限制整个考试会话，而不是给一个窗口配置第三方进程捕获白名单。辅助应用获准运行／联网不意味着获准屏幕录制。自身原始帧编码与 AAC 组合仍需获批后的独立验证。[D10–D17、D19–D21]
4. macOS **26.1** 起存在 `AEAssessmentConfiguration.allowsScreenshots`，但范围仅为复制到剪贴板的截图，不能写成“可允许自有录屏进程”。正式策略应保留默认 false，除非考试需求明确允许这类截图。[D16]

## 一、.none：官方描述与本机现象怎样同时成立

### 核对到的事实

| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 当前枚举文档称 `.none` 为 legacy，要求不要靠它隐藏或排除捕获内容 [D01] | Apple 当前不把它推荐为防捕获安全边界 | 不能据此抹掉某版本的实际不可捕获现象 |
| 同一文档又说明它可能使内容在某些共享场景不可用 [D01] | 官方本身保留了“某些路径仍受影响”的描述 | 没有列出受影响 OS／API／硬件组合 |
| 当前 SDK `NSWindow.h` 仍保留旧注释，`CGWindow.h` 的旧截图接口也写明排除 sharing-none | 历史机制和接口契约曾涉及窗口可读性，属性仍可设置 | 不能把旧截图注释外推到 SCK 的所有路径；也不能等同现代完整支持 |
| 本机主矩阵与 `.none` 更新／重建流补测均未检出合成秘密标记 | 在已记录配置、时间和样本中确有影响 | 不能证明所有 filter 构造、所有第三方应用、其它 OS 版本也如此 |
| Apple 论坛 808016：发帖人报告初始 SCK 流隐藏、改变捕获类型／排除应用后可见；DTS 要求提交小工程调查 [D03] | 存在需要 Apple 调查的不一致报告，DTS 没有给出稳定保证 | 发帖人的描述不是本项目实测，DTS 的回应也没有确认内部机制或精确修复版本 |

建议正式报告采用以下措辞：**“本机观察到 .none 仍影响所测捕获输出；Apple 当前明确不建议将其用于保证防捕获。其现代可靠性没有足够公开契约，保留为兼容和对照机制。”**

不要采用“macOS 15 后 .none 必然完全无效”“SCK 永远绕过 .none”或“只要重新设置 sharingType 就恢复所有路径保护”等绝对结论。这些都超出本次官方证据与本机实验。

### 仍需向 Apple 澄清的具体问题

- `.none` 文档中 legacy 说明与某些共享场景仍受影响，分别指哪些受支持语义？有没有对当前 SDK 链接版本和运行版本的差异说明？
- 对包含 `AVSampleBufferDisplayLayer` 与普通 AppKit 控件的窗口，SCK 单帧、窗口流和显示器流是否预期采用不同遮蔽粒度？
- 过滤器更新是否需要覆盖窗口、应用、显示器来源之间的切换，而不只是以等价来源替换 filter？
- 可否提供受支持的 `preventsCapture` 硬件／系统范围和故障时的 fail-closed 行为说明？

这些是**待提交的技术问题**；本轮没有向 Apple 发消息、提交 Feedback 或替用户申请 entitlement。

## 二、Clear Key：实验到底缺什么

### API 与媒体前提

`AVPlayer.allowsCaptureOfClearKeyVideo` 从 macOS 26.4 可用，默认 false。文档明确涉及截图、录屏、`AVPlayerItemVideoOutput` 和 ScreenCaptureKit，并明确不影响 FairPlay Streaming。[D04]

较早的公开接口 `AVContentKeySystem.clearKey` 和 `AVContentKeyResponse(clearKeyData:initializationVector:)` 从 macOS 10.13 可用：应用可向 Clear Key 请求提供解密密钥和 IV，不需要把所有密钥交付都误写成 FPS 的 SPC／CKC 交换。[D05、D06]

Apple TN2454 给出测试方法：保留 SAMPLE-AES 媒体，将 key format 改为 identity，提供匹配的 16 字节内容密钥、匹配 IV 和可取得的密钥文件 URL。它明确将这种方法用于测试，不建议如此部署生产内容。当前 HLS 说明也指出 identity 的密钥 URL 就是密钥文件来源，并且这种交付方式保护能力有限。[D07、D08]

因此，真正缺失的条件应逐项描述：

| 条件 | 本轮进度／验收方式 |
|---|---|
| 加密方式准确 | 使用 Bento4 `mp42hls --encryption-mode SAMPLE-AES` 生成 MPEG-TS 样本加密；不是仅替换 m3u8 标签，更不是整段 AES-128 |
| 匹配的 key／IV／manifest | 本地测试 key 为固定 16 字节，IV 由工具产生并写入 manifest；源、命令、工具 commit 和每个输出 SHA256 归档 |
| 可控的合法素材 | 复用此前合成考试 Demo 的明文自录；不使用真实试题或受版权 DRM 限制的节目 |
| 播放器确实完成解密 | 三组及顺序对照均 ready、时间推进；挂接 VideoOutput 的四组均取得有效像素；未将 ready 状态单独当作显示验证 |
| false／true 是唯一关键差异 | 新 ClearKeyDemo 使用普通窗口、AVPlayerLayer，不额外设置 sharing-none 或 preventsCapture；分别运行明文 false、SAMPLE-AES false、SAMPLE-AES true |
| 同进程视频输出 | false 主组复制 239 次、8 张采样均明文；先 false 后挂接的补组复制 107 次、4 张采样均明文。这与文档广义描述不一致，不保证可长期依赖 |
| 外部捕获 | 三组共 143 张外部图：plain false 47／47 和 encrypted true 47／47 命中；encrypted false 0／49 命中。两组顺序补测的 34 张外部图也未命中；全图 OCR＋ROI 检查 |
| 本机肉眼显示 | ClearKeyDemo 与原有 SampleBuffer Demo 是不同播放路径，原有人工作答确认不能自动转移到新实验 |

本轮在 Apple 当前 HLS 示例页、API 页面和公开开发者资料中，**未找到专为 26.4 此属性提供的完整官方端到端示例或已标明 Clear Key、同时提供匹配 key／IV 的现成测试流**。这是检索结果，不是断言这种素材绝不存在。官方已经提供足够的格式与 API 依据，因此本轮选择生成可审计的合成测试素材。[D09]

### 本轮实现与证据目录

- `research/clearkey/Bento4/`：Bento4 官方仓库源码，commit 记录在 `media-generation.json`；仅作本地研究构建，没有安装系统驱动。
- `scripts/prepare-clearkey-media.py`：生成明文和 SAMPLE-AES 两组 HLS。
- `research/clearkey/media-generation.json`：源 MP4 SHA256、工具版本、命令、manifest 与全部媒体文件 SHA256。
- `research/clearkey/media/`：本地 HLS、测试 key、分片；只从 `127.0.0.1:8766` 提供，不绑定外部接口。
- `research/clearkey/encrypted-offline-decoded.png`：FFmpeg 使用匹配密钥成功解密后的素材有效性对照。它不是 AVPlayer 捕获行为证据。
- `Sources/ClearKeyDemo/main.swift`、`scripts/build-clearkey-demo.sh`、`scripts/run-clearkey-matrix.py`：原生三组测试；另外增加 after／none 初始化对照，真实结果见 [ClearKey有效媒体实验.md](ClearKey有效媒体实验.md)。

本轮 false/true 的外部捕获差异已经观察到，但只说明特定媒体播放链在本机的行为，不能把属性设置到闲置 AVPlayer 上从而保护普通试卷 UI。true 若允许截图和 SCK，会同时扩大外部捕获面；它不是只允许自己录制的开关。UI 转为加密媒体还要评估编码、分片、缓冲与交互延迟，不能用本地 VOD 播放成功替代实时考试架构性能验证。

## 三、AAC：考试产品可申请，但边界应写准确

### 申请资格和当前稳定 API

Apple 将 AAC 用于教育测评、考试等高风险评估；官方明确提供 entitlement 申请入口。考试星这样的考试应用属于可以提交用途说明的场景，但是否获批由 Apple 决定。本轮没有访问账户登录或代为申请。[D10、D11、D22]

| 能力 | macOS 可用版本 | 解释 |
|---|---:|---|
| `AEAssessmentSession`、核心配置与 entitlement | 10.15.4 | 申请获批、签名与 provisioning profile 均须正确；调用 begin 后等待 delegate 确认 |
| 辅助应用 `AEAssessmentApplication`、`AEAssessmentParticipantConfiguration`、配置增删与 update | 12.0 | 允许指定应用参与会话及独立配置网络权限；不是任意进程的捕获授权 |
| `supportsMultipleParticipants`、`supportsConfigurationUpdates` 查询 | 14.5 | 运行时检查平台支持；查询出现版本不能反推参与者功能本身直到 14.5 才存在 |
| participant `configurationInfo` | 15.0 | 公共字典属性，但没有文档化的通用 capture-allow 键；不能自行发明键值 |
| participant `isRequired` | 26.0 | 参与者需求配置，不能解释成允许截屏 |
| `allowsScreenshots` | **26.1** | 默认禁止；仅针对剪贴板截图，见下文 |
| `allowsAccessibilityKeyboard`、Live Captions、Reader 等配置 | 26.1，各属性需分别核对 | 支持考试无障碍策略配置，不应笼统禁用无障碍 |

上述版本核对自本机 macOS 26.5 SDK。在线文档及 WWDC26 还包含 **macOS 27** 新功能，例如系统预检查、更多菜单／Dock 配置、限制只有参与者运行、非 bundle 可执行文件参与者等；**不能写成 macOS 26.6.2 本机已经可用或已测**。[D13、D14、D22]

### 默认防截屏与有限例外

Apple 的 AAC 概览及分发指南明确列出阻止屏幕截图／录制、限制屏幕共享／镜像，并限制其它应用与网络。需要相机、麦克风等监考权限的产品应在进入 AAC 前完成授权与复查；会话内权限通知可能不显示。[D10、D12]

macOS 26.1 的 `allowsScreenshots` 专指通常由 Cmd-Control-Shift-3／4 产生、复制到剪贴板的截图，且文档说明结束会话前清空剪贴板。没有依据把它推广为允许 ScreenCaptureKit 连续录制、保存桌面录像或仅放行某个进程。[D16]

将捕获辅助程序加入 participants，也只在已公开能力范围内允许该程序参与会话及配置网络。`allowsNetworkAccess`、签名校验或 `isRequired` 都不表示豁免会话截图限制。当前 SDK 和所读官方文档中没有发现面向参与者的“允许该应用截取其它窗口”配置。[D14、D19–D21]

### 自身录制需要三分法

| “自身录制”的实际实现 | 官方依据与当前判定 |
|---|---|
| 主考试应用通过 SCK／系统截图录自己 | AAC 默认屏幕捕获限制没有文档化的同进程豁免；**不能承诺支持** |
| 加入 participants 的辅助应用通过 SCK 录考试 | 参与／联网许可不等于捕获许可；**不能承诺支持** |
| 主应用把已有自绘帧送进 AVAssetWriter／VideoToolbox | 不需要重新取得屏幕像素，在当前非 AAC PoC 中已经成功；但与真实 AAC 会话组合仍是**待获批后验证的架构推断** |

AAC 的运行条件真正缺的是批准后的 entitlement、有效签名／profile，以及可开始并结束真实会话的测试实例。仅在 ad-hoc 二进制中添加一个 plist Boolean 不会满足授权。FPS 的生产资格与 AAC 的资格是两条不同申请线，不能混为一谈。[D11]

### 获批后的最小验收

1. 在隔离测试环境运行 AAC 工程，先取得相机／麦克风等必要权限；准备安全退出及中断处理，不在考试会话中依赖调试器断点。
2. `begin()` 前不显示题目，收到 `assessmentSessionDidBegin` 后显示；记录 begin failure、interruption、end 的时序。
3. 三条自身录制路线分开测试，特别是内部帧编码是否持续、最终文件是否可解码、是否包含作答与必要上下文。
4. 在默认 `allowsScreenshots=false` 下测试截屏入口与外部捕获；如业务需要，可另开明确标识的 `allowsScreenshots=true` 对照，不能与正式防护验收混为一组。
5. 辅助应用分“不参与、参与但禁止联网、参与并允许联网”验证；同时检查 VPN／内容过滤器是否影响考试联网。
6. 包含 VoiceOver／替代输入的实际考试工作流，查验 AX 文本暴露与屏幕像素保护之间的边界。AAC 不是用来替代应用自身安全设计的承诺。
