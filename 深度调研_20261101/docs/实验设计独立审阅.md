## 1. 已经合理的设计

| 设计 | 能支持的结论 | 仍需保留的边界 |
|---|---|---|
| baseline / protected / mixed 使用同一渲染画布 | 同一显示路径下比较保护开关与普通叠加 UI | baseline 内容应确实可见且可捕获；不能只比较属性值 |
| 普通 `PUBLIC-CONTROL` 区域与 `NATIVE-LEAK` 叠加控件 | 捕获链仍能看到普通 UI；保护仅覆盖目标 Layer 的反例 | PUBLIC 只能证明窗口的一部分可捕获，不能证明视频 Layer 已显示 |
| 同进程 `SCShareableContent.currentProcess` + SCK 截图 | 测试调用者是自身进程时，该条系统截图路径是否仍遮蔽受保护区域 | 一次 SCK 截图不代表同进程所有录制 API；成功或失败均需看像素 |
| 自身 `CVPixelBuffer → AVAssetWriter` | 应用拥有的原始画布帧可独立编码 | 不是捕获 WindowServer 最终合成画面，也不自动包含普通控件 |
| 独立 Probe PID、指定 windowID、干净输出目录 | 排除把自身录制误当外部捕获，并减少旧文件污染 | 源码 SHA 还不能证明正在运行的二进制由该源码生成 |
| SCK 保留 complete/非 complete、PTS、callback 时间与错误 | 可区分帧内容、暂停/空帧和 API 错误 | 必须实际分析这些字段，退出码 0 不是捕获成功的判据 |
| `displayVerifiedByHuman=false` | 没有冒充人眼验证 | 正式结果必须维持此限制，除非另有真实观察记录 |

## 2. 初审问题记录（处理状态见上方复核表）

### P1：就绪等待超时后仍继续，可能把未显示误判为防护

`scripts/run-deep-tests.py:35–41` 的循环尝试等待 `isReadyForDisplay && submittedFrames > 10`，但退出循环后只检查 `windowID` 是否存在。只要窗口建立，即使六秒内一直没有 ready，脚本仍开始捕获。`main.swift:280–284` 的自身截图则固定在两秒触发，没有同样的就绪条件。

可能后果：源 PNG、MP4 和 PUBLIC 区存在，而视频 Layer 没有真正显示；此时外部与自身 SCK 都拍到黑区，容易产生“保护有效”的假阳性。

修正建议：显式记录 `readyGatePassed`、实际等待时长和超时原因；要求正 windowID、目标 PID 存活、renderer 无错误、ready 为真、提交数达标，否则该用例写 `inconclusive-not-ready` 并停止该次捕获。自身 SCK 使用同一 gate 并保存截图前后 state 和 host time。即使 gate 通过，它仍只证明渲染器准备状态；需要 baseline 的视频区正对照，以及物理显示独立观察才能证明目标 1。

### P1：生命周期流目前没有进入逐帧内容检查

`run-deep-tests.py:56` 仅将 `capture/*.png` 交给 InspectMedia，未包含 `capture/sck-stream-*/frame-*.png`。生命周期用例只运行流，因此它的逐帧 PNG 不在这一步的 OCR 检查范围。脚本也没有执行 `analyze-results.py`。`InspectMedia` 对 MP4/MOV 默认只解码 1 秒处的一帧。

可能后果：控制台打印 `completed`，但切换、恢复后或后半段是否泄漏没有被检查；1 秒处编码成功也不能证明整个录制连续有效。

修正建议：对流报告中所有 `saved` 文件逐个做内容检查，核对 expected 文件数/实际文件数；按阶段生成时间轴，至少包括 PTS、callback host time、SCFrameStatus、public/secret/native marker。视频验证应包含实际首/中/末帧和各阶段边界，不要只取 1 秒。需记录 AVAssetImageGenerator 的实际返回时间，避免宽松 seek 容差让多个“请求时间”实际指向同一关键帧。

### P1：最小化/隐藏只有 protected，无同场景 baseline

`run-deep-tests.py:14` 为 `window-lifecycle` 固定使用 protected。`main.swift:290` 在 4/8/12/16 秒依次 minimize/restore/orderOut/show。最小化或移出显示合成后，缺帧、停止更新、透明或背景画面本就可能发生。不能把不可见时“没有题目”计为保护成功。

修正建议：为 baseline 增加相同的 window-lifecycle/window 与 display 用例。将可见前段、最小化、恢复、orderOut、show 后段分开；不可见阶段只记捕获行为，不给防护通过结论。恢复后要求公共区/窗口重新出现并取得多帧有效样本，再比较敏感区域。窗口最小化和恢复具有动画/异步状态变化，紧随调用的 `after-minimize` 日志不是动画完成或合成切换完成的证据；应使用窗口 delegate 事件或持续状态采样作辅助边界。

### P1：动态切换复用同一秘密标记，难区分历史帧与新帧

所有模式都绘制 `EXAM-SECRET-7K9Q` 和同一洋红块（`main.swift:161–162`）。`protection-toggle` 故意在 4–8 秒把画布设为 baseline，随后切回 protected。若捕获器保留了已公开的旧帧，切回后仍识别到这个标记，不足以证明新保护阶段的新内容泄漏；反之，黑色旧帧被保留，也不足以证明保护策略已更新。

修正建议：每阶段使用唯一随机 token、递增 source frameID 和 host PTS；阶段切换时同步更新画布和日志。需要分别统计“旧公开帧延迟到达”和“保护阶段新 token 出现”。生产安全标准不能简单删除边界数帧后宣布通过：过渡帧仍要报告，稳定区间可以另做统计。普通属性 setter 返回或 `CATransaction` 提交不是所有捕获客户端缓冲区已清空的保证。

### P1：Probe 正常退出与测试 completed 并不代表媒体成功

Probe 把部分失败写入 JSON 后仍正常退出；`run-deep-tests.py` 使用 `check=True` 只校验进程退出码。`proc.wait()` 也没有检查 Demo 最终返回码。这样 API error、目标消失、0 个 complete frame、内部 writer failed 仍可能得到脚本 `completed`。

修正建议：`completed` 仅表示运行流程结束，必须另有 `observationStatus` 与 `securityVerdict`。逐项核对 report 的生命周期/错误、complete 数量、输出文件、writer final status、解码结果和有效时间跨度。缺失/错误统一归为未验证或不确定，不归为防护成功。

## 3. 时间基与事件对齐

`main.swift:182–190` 用 `CACurrentMediaTime()` 生成 PTS，未设置 `controlTimebase`，未使用 DisplayImmediately。本机 `AVSampleBufferDisplayLayer.h:43–59` 明确说明 NULL controlTimebase 按 host time 解释，且与 Core Animation 的 `CACurrentMediaTime` 相同。因此这套时间基在定义上是一致的。[Apple controlTimebase](https://developer.apple.com/documentation/avfoundation/avsamplebufferdisplaylayer/controltimebase)

剩余限制是“正确时间域”不等于“按时显示”：PTS 取自 CPU 绘制开始，enqueue 在绘制完成后才执行，大图或主线程拥堵会造成到达时已过期；`submittedFrames` 只计 enqueue，没有统计最终展示、显示迟到或 renderer 内部丢帧。`isReadyForDisplay=true` 是首帧准备状态，不能证明最新帧已到达屏幕。

动态日志使用 `CACurrentMediaTime`，Probe 回调记录 `systemUptime` 和 sample PTS。二者都可用于单调时间分析，但在没有明确校准、单位确认和捕获 PTS 源证据之前，不宜仅凭数值接近就计算亚帧级延迟。建议在两进程启动时同时采样 `CMClockGetHostTimeClock`、`CACurrentMediaTime`、`systemUptime` 并记录 clock 映射；正确换算 SCK `displayTime` 的单位。回调到达时间不能替代源画面时间。

当前场景 actions 从应用启动后定时触发，而 Probe 在就绪轮询后启动。通常可覆盖四次切换，但一旦等待接近六秒，第一个四秒动作已发生。应记录 capture-start 的 host time，并检查所有预定阶段均落在有效采样区间；更稳妥的是由捕获就绪握手后启动场景。

## 4. 同进程 SCK 对照的准确解释

`captureSelf()` 用当前进程的可共享内容找到自身 windowID，再用 `SCScreenshotManager`。本机 `SCShareableContent.h:148–153` 说明 currentProcess 返回可在无 TCC 用户同意条件下由当前进程捕获的内容；它没有承诺绕过受保护媒体。

因此，在 baseline 能完整取到视频区、protected 中普通公共区仍可见而敏感区被遮蔽的条件下，可写：“本机该次同进程 SCK 窗口截图仍受该显示保护影响。”不能写“自己的所有系统录屏都必然失败”或“自己的系统录屏已获得豁免”。当前只有一张自身截图，未测试自身 SCStream、其他系统接口、状态变化与长时录制。

自身 MP4 来自原始画布 CVPixelBuffer。它证明的是**源帧分流编码**，不是 SCK 对自身放行，且不含视频 Layer 之外的 PUBLIC 控件、mode picker、status、NATIVE 叠加 UI、系统光标/输入法候选窗。若最终产品要求录制用户实际看到的整个考试界面，需让应录制的所有考试内容进入同一个渲染源，或另外设计并验证合成路径。

## 5. 采样覆盖与 false positive / false negative

Probe 为流设置 10 fps（`minimumFrameInterval=1/10`），并在帧回调队列上同步 CI 转图与 PNG 压缩。这有利于留证，但会增加消费延迟，并可能导致 surface pool 暂停或丢帧。

| 观察 | 可成立的解释 | 不应直接给出的结论 |
|---|---|---|
| 一帧包含受保护阶段的新秘密 | 该样本存在内容泄漏，需检查阶段与源帧对应 | 仅凭旧公共 token 就认定新受保护数据泄漏 |
| 保存的全部 10 fps 样本无秘密 | 在保存并成功分析的样本中未发现秘密 | 所有 compositor 帧均无泄漏；不存在 <100ms 闪帧 |
| 最小化期间没有 complete frame | 流可能暂停/窗口不可见 | 保护成功 |
| 黑区且 PUBLIC 可见 | 普通 UI 捕获正常、视频区域不可见 | 视频在物理屏幕正常显示已获证明 |
| OCR 未识别秘密 | OCR 未检出，或内容缺失 | 内容一定不存在 |
| 只有洋红标记消失 | 固定 ROI 标记不可见 | 全部试题、控件、边缘文字都已隐藏 |
| 源 MP4 可解码一帧 | 至少该帧成功编码 | 全程无丢帧、不卡顿且与实际屏幕一致 |

逐帧像素标记和 OCR 互补，但需要人工审阅代表性整图与异常帧。若要提高短暂泄漏的发现率，可增加捕获帧率、用低负载内存统计而非在回调同步压缩每帧，并保存异常附近的帧；仍应说明所测采样率和剩余盲区。

## 6. scale=4、60 fps 性能案

`render-4x-60fps` 的画布是 900×500 **逻辑点**，scale=4 后为 **3600×2000 像素**，不能称为标准 3840×2160 的“4K”。它在当前约 900×500 点窗口上显示，因此可能是超采样后缩小，不等于在 4K 物理屏幕上进行原生显示。`backingScale` 现字段在 override 情况下是渲染倍率，建议改名或另记实际 `window.backingScaleFactor`。

| 当前指标 | 实际含义 | 不能据此宣称 |
|---|---|---|
| targetFPS=60 | Timer 请求频率 | 实际持续显示/编码 60 fps |
| renderMeanMS / renderP95MS | 当前 renderFrame 中分配、CPU 绘制、enqueue、writer append 等同步调用耗时；首帧还可能含源 PNG 写入 | GPU 完成、编码完成、输入到屏幕延迟 |
| submittedFrames | display renderer 接受 enqueue 的次数 | 实际展示帧数 |
| recordedFrames | adaptor.append 返回成功次数 | 编码文件每帧可解码且实时呈现 |
| recordingDroppedFrames | writer 不 ready 或 append 失败次数 | 整条管线全部丢帧，包括 Timer 未触发、pool 分配失败、display 不 ready |
| ps CPU/RSS | Demo 单进程的周期采样 | 整机/GPU/WindowServer/编码服务总成本或精确峰值 |

当前固定 H.264 8 Mbps：提高像素数和帧率会降低每像素每帧可分配码率，文字录制清晰度应单独验证。scale=4 每帧 BGRA 原始数据约 28.8 MB，四个缓冲区的像素数据约 115.2 MB，60 次写入约 1.728 GB/s；这些只是尺寸算术，**不是实测内存或带宽**，也没有包含 stride、额外 surface、编码引用、拷贝和复用。

性能比较还缺少相同 scale=4/60fps 的 baseline、关闭 writer、关闭 display 的拆分对照。因此不能把较高 CPU/RSS 全归因于 preventsCapture，也不能把单次 20 秒跑完等价于生产可用。应报告实际渲染次数/单调运行时长、定时器间隔 p50/p95/p99、分阶段耗时、分配与提交失败、writer 最终状态/文件时长/多时点画质，持续测试另需温度、降频和多窗口条件。

## 7. 其他可复现性问题

- `test-config.json` 当前只记录 Demo 源码 SHA-256。应记录实际 Demo/Probe/InspectMedia 二进制 SHA-256、编译参数、SDK/OS、签名信息和启动参数，避免源码改动但未 rebuild。
- `screencapture -R` 的坐标来自 `screenHeight - appKitY - windowHeight`，忽略显示器原点；仅适合已确认的主屏坐标。多屏应使用 Quartz 窗口 bounds 和显示匹配，并在每次录制前重新取位置。
- extended 用例的窗口流、显示流、application 流以及系统录屏是顺序执行，不是同一时间同步对照。长捕获或权限等待可能使 Demo 先结束；需校验每条捕获开始/结束时目标仍存在。
- `setMode` 处注释仍称自动测试使用每模式独立进程，与当前动态场景不完全一致，应在后续代码维护时更新。
- 当前窗口未提供 resize style；配置只读取一次 bounds/backingScale。因此本轮不能声称已覆盖窗口缩放、Retina 跨屏切换或色彩空间变化。

## 8. 正式报告建议采用的结论措辞

可使用：“本机已保存并检查的样本中，保护模式下敏感画布未被该捕获路径取到；同一渲染源的原始帧仍可写入视频。该结论受所测 OS、捕获接口、采样率和显示验证范围限制。”

对动态生命周期可使用：“在记录到的状态转换与采样帧中观察到……；最小化/隐藏期间的缺帧单独记为不可见状态，未作为防护通过证据。”

对于性能可使用：“3600×2000 源帧、目标 60 fps 的 20 秒试验中，同步 renderFrame 耗时为……，进程资源采样为……。实际显示帧率和输入到屏幕延迟未测。”

**优先级顺序：**先修正 ready gate 和语义错误判断 → 补逐帧/分阶段分析 → 补 baseline 生命周期和新阶段 token → 完整验证 MP4 与 same-process 对照 → 再扩展高帧率/长时性能。
