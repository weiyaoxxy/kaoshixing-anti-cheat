# 捕获探针异常与修复

日期：2026-11-01。本文件记录本轮隐藏原生源窗口测试中一次探针崩溃的直接原因、已落地的修复及一次独立复测。**它不构成原生控件保护已经整体成功的结论。**

## 1. 原始失败记录

失败调用保留在 [hidden-source-capture-invocation.json](../artifacts/controlled-smoke-20261101T130942Z/raster-baseline/hidden-source-capture-invocation.json)。当时目标为 `sourceWindowID=185647`，原生源宿主从未主动显示，AppKit frame 为 `(-10000, -10000, 900, 500)`。探针启用 `--include-offscreen`，采用 `onScreenWindowsOnly=false` 的 SCK 枚举，随后计划执行 CG、矩形、窗口和应用捕获。

该进程约 0.336 秒后以 `returnCode=-5` 结束，没有完成 `report.json`。这次失败保留为无效/不完整捕获，不计入保护成功样本。

系统产生了 `CaptureProbe-2026-11-01-184005.ips`。原始 IPS 仍在本机原来的 DiagnosticReports 目录。为避免在审阅材料内复制整机信息，本轮仅保存 [脱敏异常摘要](../research/probe-crash/CaptureProbe-20261101T131002Z-sanitized.json)，包括原文件 SHA-256、CaptureProbe 的异常、触发线程、相关参数寄存器与旧二进制 UUID；没有复制其他线程、整机标识或完整系统映像清单。

## 2. 直接原因已经确认，框架为何返回异常结果尚未确认

崩溃为 `EXC_BREAKPOINT / SIGTRAP`，终止码 5。栈顶位于 Swift 为 `SCShareableContent` 生成的 completion-to-async 桥接函数：回调参数为可选的 content 与 error，async 返回类型为非可选的 `SCShareableContent`。

诊断时，旧 CaptureProbe 二进制 UUID 与 IPS 中记录的一致：`A5E2EEEA-AE4B-3B18-B45E-7FA37E2C91A6`。对该旧二进制的反汇编显示：桥接先检查 error；error 为空时再检查 content；二者都为空会跳到相对偏移 `0x9c10` 的 `brk #1`。IPS 的相应寄存器同时为零，`x20(error)=0`、`x21(content)=0`，与该分支吻合。

因此可以确认：**这次是框架 completion 给出 nil content / nil error 后，Swift 自动 async 桥接触发 trap。** `do/catch` 不能把这种进程级 trap 当普通抛出错误接住。

尚未确认：Apple 框架为什么在当时返回了双 nil；是否与该轮的离屏枚举、系统服务临时状态、时序或其他条件有关。不能把本次直接原因擅自扩大为“所有离屏枚举都必然崩溃”。

本次栈尚未进入 `captureImage(in:)` 或 `filter.contentRect` 的浮点转 Int 路径，因此矩形越界与非有限尺寸不是这一次崩溃的直接原因。它们仍是独立需要防御的输入问题。

## 3. 已落地修复

主代理已在新目录的 CaptureProbe 源码中完成以下修复，旧轮探针及其文档未覆盖：

1. 通过 completion 形式的 `getExcludingDesktopWindows` 或 `getWithCompletionHandler` 获取内容，再自行包装 checked continuation。明确区分有 error、有 content、两者都空；双 nil 转为 `CaptureProbe.ShareableContent / code 1001` 的结构化不确定错误。
2. 矩形截图增加目标矩形与实际显示器匹配检查。完全位于屏幕外的源宿主不再作为有意义的屏幕区域截图；报告写 `skipped` 和原因。
3. 过滤器尺寸与缩放值先检查有限性、正数及配置上限，再转换为整数。异常几何写入 `invalid_filter_geometry_*` 的不确定记录。
4. 隐藏源窗口的 CG 与 SCK 调用分开留存结果，避免一条捕获路径异常使其他入口完全丢失证据。

复核位置：[shareableContent 包装及错误处理](../Sources/CaptureProbe/CaptureProbe.swift:59)、[矩形入口](../Sources/CaptureProbe/CaptureProbe.swift:347)、[filter 几何检查](../Sources/CaptureProbe/CaptureProbe.swift:377)。源码可能随后继续调整，原始调用报告和本节语义比固定行号更适合追溯。

修复后的二进制已重新构建，因此不应再要求它与失败时旧 UUID 一致。completion 包装语法在本机已通过编译检查；下述复测完成了正常枚举和错误保存，但没有再次触发 nil/nil 条件，不能写成该框架异常已能稳定重现。

## 5. 对安全结论的影响

本轮观察已经否定“隐藏源宿主必定不在系统窗口列表里”的简单假设：源窗口实际可被 CG/SCK 枚举。然而，列到窗口与取得有效像素仍是两件事。

这次没有取得有效的隐藏源窗口图像，不能据此认定视频保护已覆盖隐藏源宿主，也不能据此宣称隐藏源窗口泄露了敏感像素。当前准确记录是：**隐藏源窗口可枚举，已测按 ID 捕获入口分别返回空图或错误。**

还应在独立的合成内容对照中验证源宿主可见时该入口能够取到图像，并保持它与正式保护模式分开统计；如果后续任何源窗口入口取得敏感文字，即使呈现层被遮蔽，也必须认定整体方案在该入口未满足目标。AX、真实 IME 候选、菜单和编辑交互仍按各自测试结果评价。


## 6. 后续源窗口暴露对照改变了对生命周期的认识

`source-exposure-control-20261101T132024Z` 后续实验发现：原本 never-ordered 时无法取得有效源图的窗口，明确上屏后再隐藏，SCK 仍能按源 ID 返回可读的先前内容。独立审阅已直接检查图片。CG 在同一隐藏后阶段仍返回 nil，进一步说明不同入口不能互相替代。

这不是本节第 4 部分 never-ordered 诊断结果的矛盾，而是另一种已改变生命周期的状态：`sourceWindowEverOrderedFront=true`。由于本组 show/hide 前后使用同一 token，不能据此判断是否能获取隐藏后新写入内容。详情、截图和该批交互对照的限制见 [设计审阅第 9、10 节](验证设计与边界.md)。
