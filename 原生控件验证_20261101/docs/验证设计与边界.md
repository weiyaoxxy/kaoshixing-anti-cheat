# 原生控件保护验证设计与边界

> 执行状态补充：本文件保留设计阶段的API/实验要求口径。现已完成有限交互、捕获、源窗口及真实IME实验，实际成功、失败和待验证项请以[专项验证报告](原生控件验证报告.md)为准；不得把下文设计阶段的“待验证”误认为最终执行统计。
日期：2026-11-01。此文档是测试设计与独立审阅，**不是本轮成功结果报告**。结果必须另以原始状态、图像、视频与捕获日志支撑。先前文档和数据保留；本轮只在 `原生控件验证_20261101` 新目录新增内容。

## 1. 要回答的三个问题

1. 一个真实的 `NSTextField`、按钮和滚动区域，能否在保持合成考试业务状态的情况下，被离屏绘制为视频帧并正常显示？
2. 输入、选择、删除、按钮和滚动等交互是否改变了真实控件/field editor 状态，并完整反映在显示和自身录像中？
3. 开启显示保护后，独立捕获进程能否从呈现窗口、显示器、应用流、源宿主窗口或其他界面读到本轮合成敏感内容？

这三个问题分别判定，不能用“API 返回成功”“属性为 true”或“截图黑色”同时回答它们。

## 2. 对照模式及归因

| 模式 | 控件与呈现 | 作用 |
|---|---|---|
| direct | 真实原生控件直接显示在普通窗口 | 原生控件可显示、可编辑、可捕获的基本对照；不作为 raster-protected 唯一对照 |
| raster-baseline | 真实控件在源宿主内绘制，结果只经视频 Layer 呈现，preventsCapture=false | 验证同一离屏渲染链路可正常显示、交互和被捕获 |
| raster-protected | 与 raster-baseline 相同，仅开启 preventsCapture | 与上一行比较保护开关的实际差异 |
| mixed（如实现） | 受保护视频上叠加一个普通原生标签 | 验证保护范围，避免“所有原生子控件自动继承保护”的误解 |

主路线不同时开启 `NSWindow.sharingType=.none`。direct 成功而 raster-baseline 为空时，raster-protected 的空图只能说明链路尚未建立，不能归因于保护。普通 PUBLIC 区被捕获也不足以证明视频区域本来已经正确呈现。

源宿主窗口从建立起不要主动上屏。保存 `sourceWindowID`、`sourceVisible`、`sourceKey`、`sourceMain`、`presentationWindowID` 和主进程 PID。若为了原生编辑需要改变源宿主状态，必须记录这一行为，并检查是否引入普通可捕获内容。

## 3. 输入实验必须注明驱动层级

| 驱动方式 | 可以说明什么 | 不可宣称什么 |
|---|---|---|
| 直接设置 stringValue/状态、performClick 等内部命令 | 原生对象状态变化与重绘链路 | 不证明鼠标/键盘事件路由正确 |
| 调用 field editor 的 insertText/delete/selection 等方法 | 文本编辑器逻辑及画面同步的一部分 | 不证明真实焦点、键绑定或中文输入法有效 |
| 独立进程 CGEvent 注入 | 公共事件路径在当前权限和焦点下是否工作，须由状态/图像确认 | post 调用完成不等于目标收到；Unicode 字符投递不等于真实 IME 组合 |
| 用户直接在本机操作 | 对本次场景的物理可见性和交互确认 | 不自动扩展到其他模式、其他机器、远程接收端或所有输入法 |

每条操作保存唯一 operationID、发起方式、目标 PID/windowID、全局坐标或 key/flags、发起与处理时间、native event count、实际文本、选择范围和结果。主线程记录 `NSTextField.stringValue` 以及 `currentEditor()?.string`；两者在编辑中可能不同。以真实输出帧的文字、选区、滚动位置核验结果，不只看变量。

静态用例的捕获入口至少包含：SCK 窗口单帧、显示器单帧、矩形单帧；SCK 窗口/显示器/应用连续流；历史 CG 窗口合成/显示器直接截图；系统窗口/显示器截图及短区域录屏可作为附加入口。必须以实际执行报告为准。历史接口通过 dlsym 的兼容实验不能宣称是现代 SDK 推荐部署路线。

应用 filter 必须包含目标应用，并使用空的 `exceptingWindows`；显示器 filter 不能把 Demo 排除。源宿主的 SCK 枚举必须尝试 `onScreenWindowsOnly=false`，不能沿用旧探针仅列屏幕窗口的默认选项后宣布源窗口不存在。CG 枚举使用全窗口列表与按指定 ID 的捕获尝试；不能只检查 on-screen 列表。

## 5. 每个捕获用例的有效性门槛

- 输出目录必须是新的，记录源码和二进制哈希、系统/SDK、参数、主 PID 与捕获 PID。两进程应不同。
- 独立记录屏幕捕获权限；权限不足、目标 ID 缺失、枚举错误和 API 错误均为未验证/不确定，不是“未泄漏通过”。
- raster 模式先要求源位图包含当阶段正确内容、renderer 无错误且已有提交，再开始外部捕获。`isReadyForDisplay` 是辅助状态，不替代人眼显示观察。
- 正对照应在同一入口、相同像素尺度、同类状态下可识别当前 token；仅有 PUBLIC 工具栏不足以证明原生内容或视频 Layer 正常。
- 保存每个流的 complete/非 complete 回调、PTS、回调时间、已保存帧文件名、错误。检查报告计数与实际 PNG 数量一致，逐帧 OCR/图像解码；不能只检查第一帧。
- 阶段变化使用唯一 token 或至少单调操作 ID，并将它们写入源帧。保留边界样本；旧的公开帧和新的受保护内容泄露应分别统计。
- 静态区域可以做明确 ROI 检查；窗口移动、动画、滚动、缩放后，必须更新映射。不能用错误 ROI 的黑色判为保护成功。
- OCR 阴性不单独作为无泄露结论：同时检查图像有效性、透明度、敏感区域像素/结构变化和代表图人工查看。复杂小字、选区颜色和输入候选应另作视觉检查。

## 6. 本轮最关键的失效模式

**源内容可被另一条路径获取。** 视频呈现被遮蔽，但原生宿主窗口仍能按 ID 获取敏感文字，则方案整体未满足目标。若源窗口没有有效可用 ID或不能枚举，只能记录本机已测入口的状态，不能证明任意系统/任意捕获方法都无法访问。

**编辑器没有进入源图像。** 程序状态已经改变，但离屏位图仍显示旧 stringValue；或者只缓存标签外观，不含正在编辑的 field editor、插入点和选区。此时不是“编辑成功且受保护”，而是画面同步/控件适配问题。

**真正可见的原生文本仍在其他窗口。** 候选框、自动补全、右键菜单、tooltip、系统拼写/写作面板等可能在单独的视图或窗口中；既有视频 Layer 不自动证明覆盖它们。看不到候选框也可能是坐标转换错误，不代表候选内容被安全保护。

**在屏与离屏坐标不一致。** AppKit 视图 point 坐标、CG 屏幕坐标、Retina pixel 和输入法字符矩形不同；点击位置正确、滚动结果正确、候选位置正确应分别核验。不能把 CGEvent.post 无错误当输入成功。

**为了隐藏信息而损坏无障碍。** 输出只剩通用 AX group 可以减少某些文本暴露，但不会提供完整原生读屏功能。截图保护与 AX 内容策略需要分别决策、分别测试。

**原生输入局部成功被泛化。** 一个 NSTextField 的 ASCII 插入可行，不等于 NSTextView 富文本、复杂表格、WKWebView、Electron、SwiftUI、第三方内容或系统对话框均可用。新增控件应按其实际渲染和交互路径验证。

## 7. 结果用词与可交付判定

| 可使用的措辞 | 必要证据 |
|---|---|
| “真实原生控件外观已进入受保护帧” | 源对象类名、源帧、baseline 外部图像、protected 自录/物理显示证据对应 |
| “CGEvent 驱动的 ASCII 编辑可用” | 独立输入工具权限/事件日志、目标实际文本/选区变化、源帧和显示对照 |
| “原生输入法协议代理已部分验证” | marked/insert 协议操作及实际编辑器状态；必须注明是否真实 IME |
| “真实中文 IME 本次验证通过” | 实际输入法组合/候选/提交操作、位置及捕获证据；不能仅用程序设置中文字符串 |
| “当前入口未捕获到敏感像素” | 入口有效、正对照可读、源内容存在、输出逐帧检查；保留采样间隙和系统范围 |
| “原生控件通用防截屏已实现” | 本轮有限 PoC 无法支持这一泛化结论 |

充分验证不等于穷尽验证。最终报告应明确本机/系统版本、实际入口与样本、手动/自动驱动层级、未执行的输入法/无障碍场景、短时采样盲区及生产集成限制。报告中的通过项只能来自实际已产出的证据。

依据见 [Apple API 与 SDK 核验](../research/native-api-evidence.md)。

## 9. 已显示源窗口再隐藏：存在可回采的反例

独立审阅了 [source-exposure-control-20261101T132024Z](../artifacts/source-exposure-control-20261101T132024Z) 的操作日志、状态、捕获报告，并直接打开检查了 [隐藏后的 SCK 源窗口截图](../artifacts/source-exposure-control-20261101T132024Z/source-hidden-after-visible-screenshot/sck-screenshot-window.png)。图片中 `EXAM-SECRET-7K9Q`、`NATIVE-EDIT-6T2W`、`INPUTSECRETSOURCECONTROL8K2P` 以及滚动区域文字清楚可读。

该实验中，呈现窗口始终为 raster-protected，源宿主 ID 为 185766。步骤与结果如下：

| 源宿主阶段 | 状态 | CG 指定源窗口 | SCK 指定源窗口 |
|---|---|---|---|
| 从未上屏 | visible=false，everOrderedFront=false | nil_image | -3811，无有效图 |
| 主动 showSource | visible=true，everOrderedFront=true | 有效图像 | 有效图像 |
| hideSource 之后 | visible=false，everOrderedFront=true | nil_image | **1800×1000 有效图像，敏感合成内容可读** |

根据 [harness-actions.json](../artifacts/source-exposure-control-20261101T132024Z/harness-actions.json)，唯一输入 token 在 showSource 前设置，showSource、hideSource 和后续回采期间均未改变。因此，本组证据直接支持的是：**此前显示过的源窗口内容，在隐藏后仍能通过本机这次 SCK 窗口捕获取得。** 它还不能区分保持旧内容的缓存回采与持续取得最新源像素，也不能证明隐藏期间后来写入的新 token 已泄露。主代理正在用隐藏后更换唯一 token 的独立用例补测；结果另记。

这项反例必须与默认 never-ordered 原型分开统计。该源宿主是为了正对照由实验明确调用 showSource 暴露的，状态已标 `sourceExposureTest=true`，不应把它伪写成默认原型在源窗从未显示时已发生同样泄露。反过来，也不能因为这是诊断模式而忽略其架构含义：**orderOut/isVisible=false 不能被当作先显示原生窗口后再隐藏即可恢复安全的保证。**

对生产设计的要求是明确维护源窗口生命周期，记录和检测非预期 orderFront/激活/附属窗口行为。若发生过源界面暴露，应把会话记为边界被破坏；不能只调用 hideSource 后继续宣称已消除所有可回采内容。销毁重建是否足够也需另外验证，且无法撤回此前已被捕获的画面。

四个模式的 `validity.json` 即使均记录 processExitCode=0、writerStatus=2、rendererError 为空，也只说明应用/录像流程状态，并不能覆盖交互检查中已出现的问题。**该批不能被整体称为“四模式全部有效且通过”的最终矩阵。** 修复后应新开目录重跑，保留这批初始问题，不用新数据覆盖旧日志。
