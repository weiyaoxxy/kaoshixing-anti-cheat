# UU 测试副本的签名与启动依据

日期：2026-11-01。本文是 Hook 综合研究报告的证据附件，针对“原版 UU 无法通过既有 DYLD 启动方法加载库后，如何在隔离副本中继续验证”。只读检查原应用、系统 plist、已有运行采样和 Apple 官方材料；本文作者没有启动、结束、重签第三方程序，也没有修改任何 launchd 任务。

结构化结果见 [launch-and-signing-review.json](../research/launch-and-signing-review.json)。本次只保存公开签名、依赖路径、固定符号词表命中和筛选后的 plist 字段，没有读取或记录运行进程的完整参数、远程凭据或业务字符串。

## 1. 已确定的真实组件与尚未知的启动参数

原版为 `/Applications/UURemote.app`，4.40.0 / build 621。既有已连接实验中，Server PID 84053 的父进程是 Service PID 84016，Server 的运行时采样证实其 SCK 接收回调进入 `libstreamer.dylib` 的屏幕帧处理路径。这可以确定后续应优先验证真正的 Server 宿主，不能只以 GUI 加载为目标。见 [运行采样独立复核](../../artifacts/uu-live-connected-20261101T144107Z/review.json)。

原用户任务信息：

| 项目 | 原版值 | 含义 |
|---|---|---|
| plist | `/Library/LaunchAgents/com.netease.uuremote.agent.plist` | 此文件只读，未经修改 |
| Label | `com.netease.uuremote.agent` | 当前用户 launchd 任务标识 |
| ProgramArguments | 原版 `Contents/MacOS/UURemoteService`、`-agent` | `-agent` 来自 plist，是已确认的启动参数 |
| MachServices | `com.uuremote.agent.controlled`、`com.uuremote.agent.controller` | 固定的用户域 IPC 服务名 |
| RunAtLoad / KeepAlive | true / true | 现有任务会保持运行；另开副本不等于原任务自动切换 |
| LimitLoadToSessionType | LoginWindow、Aqua | 原任务配置的会话类型 |
| root 任务 | `com.netease.uuremote.daemon`，Mach 服务 `com.uuremote.daemon` | 本轮不修改、不重签、不替换 |

Service 中存在 `NSTask`、`setExecutableURL:`、`setArguments:`、`launchAndReturnError:` 以及 `launchServer` 子串线索；root Daemon 含有原 `/Applications/UURemote.app` 及 Server 相对路径词。它们说明存在启动与 IPC 相关代码，**不能据此证明副本 Service 会从自己的目录启动副本 Server**。程序也可能由其他组件传入路径、参数或连接配置。

`-server`、`-user` 等仅在固定词表的“子串命中”中出现，未被确认是独立命令行参数，不能拼装成运行命令。没有执行第三方 `--help`，也没有导出当前 Server 的完整参数。已有真实父子关系和实际捕获栈，没有补上 Server 初始化协议这一缺口。

## 2. 完整复制 bundle 后的动态库条件

原 GUI 与 Server 都依赖 `@rpath/libstreamer.dylib`；Service 的直接依赖里没有这个库。arm64 与 x86_64 两个架构的相关 rpath 一致：

| 组件 | LC_RPATH | 在完整副本中的推断 |
|---|---|---|
| GUI | `/usr/lib/swift`；`@executable_path/../Frameworks` | 对应副本 `Contents/Frameworks` |
| Service | 上述两项；`@executable_path/` | 能保留相同目录结构，但是否启动副本 Server 仍未知 |
| Server | `/usr/lib/swift`；`@executable_path/../Frameworks`；`@executable_path/` | Server 在 `Contents/Helpers`，其 `../Frameworks` 正好是同一副本的库目录 |
| libstreamer | `@loader_path/../lib` | 库本身还有这一路径设置；其主要依赖是系统框架 |

因此推荐完整复制 `.app` 后通过副本 Server 的绝对路径启动；单独复制 Server 可执行文件会失去原有相对依赖布局。上述是 Mach-O 静态依据，尚不是“副本实际已经加载本地 libstreamer”的证据。后续必须通过运行时映射核对 Server 与 libstreamer 的实际路径，防止测试实际落在原版组件上。

不要只用 `open -a UURemote` 判断副本路径。这类按应用名称或身份寻址的启动方式，不能单凭命令成功证明运行的是哪个副本。固定 bundle ID 还可能带来原 GUI 激活、单实例或服务重用；这些属于待验证行为。

## 3. 重签究竟改变什么

原 GUI、Service、Server、Daemon 均由厂商 Team ID `PU9BNSBJW7` 签名并启用 Hardened Runtime。Service 没有 entitlement；Server 有 `com.apple.security.device.audio-input=true`；GUI 有 audio-input 和 bluetooth。原签名未开启 `allow-dyld-environment-variables` 或 `disable-library-validation`，原版 GUI / Service / 新 Server 的最小库实验已记录“构造事件 0，映射检查成功但见证库映射 0”。这不是全部加载技术的否定，足以作为本次方法的原版负对照。

Apple 的公开机制支持两个独立条件：宿主允许 `DYLD_` 环境变量，以及宿主允许载入不满足默认 Team ID 规则的库。是否生效要看**实际运行的宿主可执行文件**签名，给 witness 或 hook dylib 添加相同 entitlement 不能替宿主授权。[Apple：Allow DYLD environment variables](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-dyld-environment-variables)、[Apple：Disable Library Validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)

在用户可写副本上，可以把 ad-hoc 签名与 `runtime` 及两项例外组合为本地诊断变量。当前系统自带 `codesign(1)` 明确把 `-s -` 定义为 ad-hoc 签名，并把 runtime 定义为自 macOS 10.14 起启用强化运行时限制、可由 entitlement 选择性放宽。**这只是允许构造待测签名条件，不是已经证明此 UU 副本可连接、可取屏或可 Hook。** 原始手册来源 `/usr/share/man/man1/codesign.1` 的 SHA-256 已纳入 JSON。

应保留目标可执行文件确实需要的原有 entitlement，再只为受测宿主增加两项例外；不要向每个 framework / dylib 机械复制宿主 entitlement。不要保留一条要求原厂商证书的旧 designated requirement，却期待新的 ad-hoc 签名仍满足该要求。ad-hoc 不包含原厂商签名身份，也不继承其 Team ID、信誉、授权关系或原公证结果。

Apple 要求复杂 bundle 按依赖从内向外签名，并不建议使用 `--deep` 统一签名；原因包括嵌套组件需要不同签名选项、部分非标准位置的代码未必被发现。[Apple：Creating distribution-signed code for macOS](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac)

对本测试副本的操作顺序建议是：先完成需要改动的嵌套 Server / Service 签名，其他没有修改的库和 helper 可保留各自原签名；最后重新封装外层 app 的签名，使其资源封印反映当前嵌套组件。若外层主程序也被改为 ad-hoc 并保留 runtime，需重新考虑它加载原签名库时的 library validation 条件，不能只处理 Server 然后假定 GUI 一定正常。每个实际执行的宿主都应记录自己的签名和例外，最后做严格递归验证。验证成功只证明磁盘签名结构满足该检查，仍不保证 TCC、IPC、Gatekeeper 或程序业务流程接受。

## 4. “文件副本”还不是完整运行隔离

复制和重签会隔离磁盘上的代码修改，不会自动隔离偏好设置、账号状态、网络设备身份、固定 Mach 服务名和与 root Daemon 的连接。不能把同名副本视为一套必然独立的远程服务。

| 障碍 | 已知事实 | 合理推断与验证要求 |
|---|---|---|
| Mach 服务冲突 | 原用户任务占用两个固定服务名 | 仅改新 launchd Label 不能改变程序查找的 IPC 名；重复注册或连接原服务都可能发生 |
| root Daemon 关联 | 存在固定原应用路径词和 daemon Mach 服务 | 副本可能依赖原控制链，或被原链要求启动原路径；尚未观察副本行为 |
| IPC 身份验证 | 原组件有不同签名 identifier；用 NSXPC 通信的静态线索明确 | 新 Team ID / ad-hoc 可能不被对端接受；本轮没有证明 UU 具体采用了哪种签名校验 |
| TCC 屏幕录制、辅助功能 | 既有权限是原应用运行条件 | 不能假定改签副本继承；需观察系统提示与实际捕获返回，不能写 TCC 数据库强行授权 |
| 路径及资源 | 副本 bundle 完整结构可保留 rpath | 可能仍有配置、单实例锁、路径限制；必须记录实际 PID / 路径 / 库映射 |
| 登录与连接初始化 | 真实 Server 原来由 Service 创建 | 直接启动可能因缺少参数或 IPC 退出；这不自动否定库加载或证明 hook 失败 |

Apple 的 TN3127 说明 designated requirement 用于识别“同一个代码”，ad-hoc 的身份绑定到特定代码版本，因此不能稳定沿用跨版本的隐私授权。对本副本而言，具体是否弹出屏幕录制权限、归属于哪个责任进程，仍需实测；本文没有查询 TCC 数据库。[Apple：TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)

Apple 同时提供 XPC 对端签名要求 API。这证明平台允许 IPC 对端依据签名拒绝连接，**不证明 UU 已使用这个具体 API**；静态搜索没有命中某个 selector 也不能排除其他校验实现。[Apple：NSXPCConnection.setCodeSigningRequirement](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement%28_%3A%29)

## 5. 建议的最小加载矩阵

下面是待执行建议，不是本附件已完成的实验。优先单独验证副本 Server 的加载；只有加载稳定且能建立真实连接，才进入 audit 和 block。每个阶段都使用明确的副本路径，原版 root Daemon 与系统 plist 保持现状。

| 阶段 | 副本签名 / 运行方式 | 观测与结论边界 |
|---|---|---|
| M0 原签名对照 | 完整原签名副本；Server 绝对路径；最小 witness | 对照此前原版 GUI / Service 负结果；没有映射不等于程序完全没启动 |
| M1 最小加载 | 新完整副本；Server ad-hoc + runtime + 原有 entitlement + allow-DYLD + disable-LV；最小 witness | 构造日志、实际 PID、库映射、真实 libstreamer 路径、退出状态；即使马上退出，也只按实际证据判定库是否加载 |
| M2 捕获审计 | M1 稳定条件下换 CaptureHook audit | 需要真实会话后证明 SCK 初始化 / 回调命中；静态符号和进程存活不够 |
| M3 远端遮罩 | 同一实际副本捕获进程与真实会话，切换 block | 基线可见 → 考试隐藏且公共计数变化 → 恢复可见；附远端证据与未注入对照 |
| Mdiag 可选诊断 | 独立新副本，ad-hoc 不启用 runtime，仅 witness | 若使用，只能说明放宽副本签名后的本地加载现象；不代表原版默认配置可用，不与 M1 混写 |

第一步可以显式执行副本 `Contents/Helpers/UURemoteServer`，传入最小 witness 所需环境，并记录它是否能活到构造函数与 dyld 映射阶段。由于没有确认业务启动协议，不应凭字符串拼接 `-server`、用户身份或连接参数。若它没有建立会话，结论应为“宿主加载验证完成 / 失败；连接初始化未完成”，不得升级为 UU 防窥成功。

副本 Service 是后续待评估入口：`-agent` 确有依据，但在原 GUI 命名空间启动它可能争用现有 Mach 服务。要同时满足“不改变原任务”和“真实副本 Service / Server 通信”，需要证明独立 IPC 命名或合法的新会话机制；当前没有这种证据。仅新建一个任务标签并复用原 MachServices 不是可靠隔离，也不应靠修改原 root Daemon 或绕过厂商 IPC 身份检查强行补齐。

## 6. 汇入 Hook 综合报告时的表述

可以写：“原版 UU 的所测加载方式未成功；真实连接的运行栈已定位 Server 的 SCK 帧处理路径。现按用户授权，在不改动原版的独立副本中研究签名条件与最小库加载。副本结论必须与原版分栏。”

只有完成对应实验后，才分别写“副本库已加载”“副本实际捕获命中 hook”“副本真实远端考试区隐藏”。即使三个阶段全部成功，也仍受 Hook 方案共同边界约束：只影响选定进程，原始像素先进入捕获进程，不是全系统窗口级保护。不得把一次副本重签实验宣传为对所有原版 UU 的无改动防护能力。
