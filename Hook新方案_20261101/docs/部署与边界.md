# Hook 新方案：部署条件、保护边界与产品化要求

版本日期：2026-11-01。审读对象为本项目 `CaptureHook` v1.2、用户级启动脚本，以及同日保存的 ToDesk / UU 证据。本文只读复核代码、签名信息和已有实验，不执行第三方进程操作。实验环境为 macOS 26.6.2（25G83）、当前用户 UID 501；SIP 的只读查询结果为 enabled。环境与组件证据见 [静态分析](远程软件静态分析.md) 和 [原始审计 JSON](../research/target-audit.json)。

## 1. 本轮能交付的结论

这是一个独立的“在指定捕获进程内改写取屏结果”方案。对本机原版 ToDesk 5.2.3.0，已经证明能经用户级 Session Proxy 启动链，把 hook 库加载进实际取屏的 Session 进程；其 ScreenCaptureKit 显示器流经处理后，用户在真实远端确认考试区域隐藏，公共计数仍然变化。恢复原启动任务后，用户又确认考试内容可见、计数正常。三阶段的人工记录、加载记录、API 调用记录与恢复证据见 [ToDesk 实机验证](ToDesk实机验证.md)。

这个结果是选定远程输出的有效干预，尚不构成“所有其他独立进程都无法获取考试内容”的系统级防护。特别是本实现先获得系统返回的原始图像，再生成遮罩副本：**原始考试像素已经进入受 hook 的远程软件进程**。因此，不能将其描述为对恶意捕获进程的隔离边界，也不能证明远程软件内部从未持有原图。要让合作软件的远端看不见，与要让不受信任的软件根本取得不了原始像素，是两个不同的验收目标。

| 结论 | 证据等级 | 当前依据与边界 |
|---|---|---|
| ToDesk 真实远端可隐藏原生考试窗口区域，公共内容继续更新 | 已验证 | 原版 5.2.3.0；本机、所测 Session、SCK 显示器流、固定窗口范围；远端证据为用户观察，没有保存远端截图 |
| 普通未注入进程仍能截到完整考试内容 | 已验证 | block 同期独立 SCK 截图与 OCR 检出考试标记；见第 3 节 |
| UU 原版 GUI 未加载最小见证库 | 已验证的负面结果 | GUI 重新启动后，事件数 0；`vmmap` 成功而见证库映射数 0 |
| UU 原版 Service 及其新 Server 子进程未加载见证库 | 已验证的负面结果 | 精确用户任务副本启动后，Service 72311 / Server 72316 映射检查成功、映射数均 0；事件数 0 |
| UU 未加载现象与其 Hardened Runtime 严格配置相符 | 官方机制与静态信息支持的解释 | 没有由这次实验取得能定位内部拒绝步骤的 dyld 诊断；不据此断言任何加载方式都不可能 |
| 任意版本、任意捕获 API、移动窗口、弹窗、多屏、HDR 都受保护 | 未验证 / 当前实现不满足全面覆盖 | 有明确的未覆盖入口、坐标假设和失败放行分支 |
| 本方案同时完成考试客户端自身可靠录制 | 未验证 | 旧方案的录像结果不能迁移为本方案证据；未 hook 的可信录制进程可作为后续独立验证对象 |

UU 证据：[GUI 最小加载结果](../artifacts/uu-load-witness-20261101T140503Z/result.json)、[Service / Server 加载检查](../artifacts/uu-service-witness-20261101T141332Z/load-check.json)。启动任务注册成功与进程运行正常，都不等于库加载成功，更不等于已经拦截 UU 的取屏或远端输出。该负面结论只针对本次保持原版签名的 DYLD 启动方法。

## 2. 原版签名和 entitlement 是部署前提

Apple 的 Hardened Runtime 用于限制代码注入等行为；例外能力由宿主可执行文件的签名 entitlement 决定，进程内库继承宿主条件。给本项目 dylib 添加 entitlement，不能替另一家公司的宿主程序打开例外。[Apple：Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)

`com.apple.security.cs.allow-dyld-environment-variables` 允许受保护宿主读取 `DYLD_` 环境变量。跨 Team ID 的库还涉及 library validation；Apple 文档说明默认验证通常要求库由 Apple 或宿主相同 Team ID 签名，`disable-library-validation` 是宿主可采用的例外。[Apple：Allow DYLD environment variables](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-dyld-environment-variables)、[Apple：Disable Library Validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)

| 条件 | 本机 ToDesk 主要进程 | 本机 UU GUI / Service / Server | 对方案的影响 |
|---|---|---|---|
| Hardened Runtime | 已开启 | 已开启 | 不能只看到 runtime 标志就断言能否注入 |
| `allow-dyld-environment-variables` | true | 未发现 true entitlement | ToDesk 的启动时 DYLD 加载具备原版签名前提；UU 对照不具备同样前提 |
| `disable-library-validation` | true | 未发现 true entitlement | ToDesk 允许跨团队库的条件不同；UU 不能因本库也有签名就自动信任 |
| `get-task-allow` | 未发现 true entitlement | 未发现 true entitlement | 本轮没有据此使用调试器实时附加或修改运行中内存 |
| 实际加载 | Proxy、Session 有构造日志和真实捕获回调 | 三个被检查进程均未见见证库映射 | 实测优先于单纯 entitlement 推断 |

上述差异来自安装版本的静态签名，不是 Apple 给本项目授予了“控制其他应用截图”的专用权限。ToDesk 以后若收紧例外、变更进程链、采用不同捕获 API 或更换签名策略，这个部署方法可能失效。Apple 的 debugger entitlement 也不是任意访问第三方受保护进程的通行证；官方明确说明目标没有所需调试许可时仍受限制。[Apple：Debugging tool entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.debugger)

本轮没有修改或重签 ToDesk / UU 的 `.app`，没有获得管理员权限或以 root 身份执行实验，没有修改 SIP，没有向 root Service / Daemon 注入，也没有借助新授权改写 TCC 数据库。ToDesk 原 plist 及四个关键可执行文件与基线 SHA-256 一致，见 [原文件保留检查](../artifacts/todesk-block-20261101T135207Z/original-files-preservation-check.json)。最终对两家软件共 34 个基线 Mach-O 文件再次核对，全部 SHA-256 未变化，见 [最终恢复与完整性检查](../research/final-restoration-check.json)。这证明这些被测文件内容未变，不能代替对安装包非 Mach-O 文件或完整系统状态的认证。远程软件依赖其原有取屏权限；本 hook 既不授予也不替代这些权限。

## 3. 生效单位是进程和调用路径

当前 hook 由 C 函数 interpose 和 Objective-C 方法替换组成，在被加载的进程内包裹取屏返回值或回调。它没有修改 WindowServer 的全局窗口捕获策略，也没有让原生考试窗口变为 DRM 受保护窗口。

明确反例保存在 [独立未注入探针结果](../artifacts/todesk-block-20261101T135207Z/independent-unhooked-check/scope-check.json)：ToDesk block 实验期间，另一个未加载 hook 的进程通过 SCK 截图仍检出考试秘密标记。对应 [本地截图](../artifacts/todesk-block-20261101T135207Z/independent-unhooked-check/sck-screenshot-window.png) 可查看原生输入框和完整考试内容。它不是 ToDesk 的远端截图，恰好证明该方案只影响受控路径。

库已加载到 GUI 不代表已经覆盖后台 Server；父进程存在环境变量不代表每个子进程都会继承并接受。新的 Session、辅助捕获程序、另一个用户域、系统进程或重新启动而未带库的实例，都要重新确认加载和调用命中。现有代码也没有覆盖静态分析发现的全部入口，例如未对 `CGWindowListCreateImageFromArray` 实施 C interpose。静态符号存在不能证明软件实际使用它，但足以否定“所有潜在路径已覆盖”的表述。

配置中的 `ownerPID` 目前用于描述目标，遮罩计算没有据此建立身份校验。普通可写 JSON、窗口 ID 与屏幕矩形不能充当防篡改策略或可信证明。即使补全所有目前已知 API，能够主动改变自身调用方式或读取自身原始缓冲区的程序仍不受此机制可靠约束。

## 4. 当前实现遇到异常会放行原图

源码依据：[CaptureHook.m](../Sources/CaptureHook/CaptureHook.m) 的 `Target`、`MaskRect`、`RedactImage`、`RedactSample` 与 `WrapDisplayHandler`。当前优先保留第三方程序的运行与返回语义，没有实现严格的失败阻断。

| 情况 | 当前代码行为 | 审阅时应如何判定 |
|---|---|---|
| 目标配置缺失、无效或 `enabled=false` | 不遮罩，返回原图 / 原 sample | 不是保护成功；不能只看进程仍活着 |
| 未知捕获范围、源区域裁切、宽高映射比例不匹配 | 记录原因并放行原数据 | 不支持的配置可能直接暴露考试内容 |
| SCK / DisplayStream 视频帧为非 BGRA、平面格式 | 原数据传递 | 未支持 NV12、HDR 等帧布局，不可类推 |
| 新缓冲区分配、锁定或 sample 创建失败 | 原数据传递 | 内存压力下不提供可靠阻断保证 |
| SCK 回调不含 image buffer | 原 sample 传递，记录 `no_image_buffer` | 本次回调没有可涂黑的像素；不能记为已保护图像帧，也不能仅凭这个字段断言发生泄露 |
| 截取目标之外的窗口 / 区域 | 按设计保持原图 | 应与真正异常分开统计 |

还发现一处日志准确性限制：`RedactImage` 在 `CGBitmapContextCreateImage` 后先写 `image_redacted`，最终返回却允许在结果为空时回退原图。因此该事件并非在所有失败分支上都严格证明返回了遮罩图像。本次 ToDesk 实测走 SCK 视频 sample 分支，该图片路径问题不是已观察到的 ToDesk 泄露，但交付产品前应改为根据最终返回结果记录状态并做故障注入验证。

ToDesk 的帧日志也为抽样记录，不能把日志条数当作全量视频帧数，更不能把 `redacted` 字符串当作远端截图。已采集到的无图回调没有保存足以逐个判定完整帧状态的元数据，不能全部推断为 idle。每阶段实际结论以 [实机证据说明](ToDesk实机验证.md) 为准。

## 5. dirtyRects、窗口运动与弹窗尚未形成闭环

Apple 说明 SCK 帧带有变化区域和内容映射信息；接收方可以仅用变化区域更新已缓存画面。当前代码复制了原 sample attachments，`CGDisplayStream` 包装也保留原 `CGDisplayStreamUpdate`，没有把遮罩策略额外造成的变化写回这些元数据。[Apple：SCStreamFrameInfo](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo)、[Apple WWDC22：Take ScreenCaptureKit to the next level](https://developer.apple.com/videos/play/wwdc2022/10155/)

这会产生需要专门验证的风险：开启保护、移动遮罩、改变窗口范围时，修改后的像素区域未必全部包含在系统原始 dirtyRects 中。如果远程软件按这些元数据做增量传输，远端可能沿用旧缓存。当前 ToDesk 固定范围实验没有观察到该问题；这不是实测泄露结论，也不能因为一次隐藏成功而排除此类状态转换问题。

| 场景 | 当前实现限制 | 后续验收需要的证据 |
|---|---|---|
| 保护开启 / 关闭，静止画面 | 遮罩变化未主动更新 dirtyRects 或要求完整刷新 | 从远端预先显示秘密开始，切换保护并验证旧缓存完全清除 |
| 快速移动、拖拽缩放、跨显示器 | 配置由事件与 1 秒定时器更新，与捕获帧没有共同序号或严格时间匹配 | 高帧率远端录像，覆盖旧 / 新窗口区域及中间帧；验证时间戳和配置版本 |
| SCK 更新 filter / configuration | 完成回调才更新缓存范围，可能存在在途帧 | 记录每帧实际映射和变更代次，验证切换窗口 / 显示器 |
| 不同缩放、留黑边、区域裁切 | 目前用显示器矩形与输出尺寸估算；未逐帧使用 `contentRect` / `contentScale` / `scaleFactor` | 每种 Retina 比例、裁切、旋转、负坐标布局的像素级核对 |
| 菜单、输入法候选、提示、拖拽预览、系统对话框 | 当前只配置一个考试窗口矩形，其他窗口超出部分不会自动纳入 | 在真实输入操作中识别所有相关窗口归属，并验证弹出与消失全过程 |
| 最小化 / 隐藏 / 退出 | 原生 Demo 会把配置设为 disabled；策略没有等待所有在途捕获和缓存清理完成 | 验证状态转换、后台窗口捕获及恢复的首帧 |

窗口内真实 `NSTextField`、`NSTextView`、按钮等仍由 AppKit 正常呈现，hook 在取屏输出侧处理像素，所以方案不要求把这些控件重新绘制成视频。但此次远端验证不等于已经完整验收中文输入法、VoiceOver、无障碍 API、剪贴板、拖拽数据或文档导出。屏幕像素遮罩也不会自动阻止这些独立的数据访问通道。

## 6. 可回滚部署仍需管理进程生命周期

[ToDesk 启动工具](../scripts/todesk-proxy-instrument.py) 只替换当前用户 GUI 域的精确任务定义：把原 plist 复制到新的实验目录，在副本配置环境变量，然后卸载 / 注册指定 label。原 `/Library/LaunchAgents` 文件保持不变；恢复时核验其 SHA-256 并从原路径重新注册。

真实实验出现过一次 `bootstrap` 返回 5，当时原任务已再次注册；脚本自动恢复记录保存在 [第一次 block 失败证据](../artifacts/todesk-block-20261101T135028Z/instrumentation-state.json)。现有证据不足以确定是谁重新注册，不能写成厂商主动反 hook。这个失败说明启动任务存在并发竞争，不能将 `launchctl` 单个返回码当作最终状态。

恢复 launchd 任务定义不会把已加载的库从旧进程内卸载。脚本不强制杀掉仍存活的 Session / Server，实际测试必须核对当前承担连接的 PID、是否有旧实例存活，以及远端是否重新连接到新的会话。本轮 ToDesk 已完成原任务恢复与用户恢复确认；详细证据见 [恢复确认](../artifacts/todesk-block-20261101T135207Z/human-recovery-observation.json) 和 [恢复状态](../artifacts/todesk-block-20261101T135207Z/last-status.json)。

最终恢复检查还确认 ToDesk 与 UU 的用户级任务均从原 `/Library/LaunchAgents` 来源运行，任务定义没有本实验的 `DYLD_INSERT_LIBRARIES` / `HOOK_DEMO_*` 环境项。UU 已按原方式重新运行 GUI、Service 和 Server；截至记录时尚无用户远端恢复确认，因此仅能认定本机任务与进程恢复，不能认定 UU 连接已通过人工验收。见 [最终恢复检查](../research/final-restoration-check.json)。

现有无管理员实验只说明“该用户可管理自己的既有 GUI 任务，且这一版 ToDesk 的原签名容许所测加载方式”。它不代表可以无管理员管理 root 服务，或可以让任意软件接受库。项目未实施关闭 SIP、修改系统组件、重签厂商应用、修改根服务或私有驱动等另一类部署方式；不能把这些尚未完成的操作写为通用解决办法。

## 7. 产品化判断与下一步门槛

**可作为受控环境、指定 ToDesk 版本的原生 UI 遮罩 PoC；尚不能作为面向任意远程软件的通用考试防截屏产品交付。** 对 UU 当前结论是该原版 DYLD 加载入口没有成功，尚未形成其真实远端遮罩演示。

面向合作厂商的产品路线更明确：由远程软件在自己的取屏和编码链中接入有版本合同的窗口排除 / 像素遮罩能力，同时负责增量刷新、弹窗归属和会话状态；若只需限制其输出，也可以在厂商可控制的 SCK filter 中实施窗口或应用排除。公开 API 可供捕获方这样使用，不等于考试应用能强制别人的 filter。应优先采用显式集成或受支持插件，不以长期保留任意 DYLD / library-validation 例外作为产品前提。

| 交付门槛 | 必须补齐的工作 |
|---|---|
| 部署可靠性 | 明确支持的厂商版本、签名和架构；每个真实捕获进程的加载证据；重启、升级、重连与回滚验证 |
| 保护完整性 | 规定不支持 / 配置异常时采取暂停传输、全帧遮挡或阻止开考等策略，避免静默放行；不得仅依赖状态日志 |
| 画面正确性 | 合并系统变化区域与遮罩变化区域；必要时请求完整刷新；处理在途帧、缓存和时间一致性；覆盖多窗、弹窗、多屏与颜色格式 |
| 性能与稳定性 | 当前逐帧 CPU 全帧复制，尚无 CPU、内存带宽、帧延迟或长时稳定性基准；应验证不同分辨率、帧率、内存压力和生命周期 |
| 自身录制 | 建立可信录制进程 / 路径并独立验证；清楚区分“可信录制可见”与“未控制的其他进程同样可见” |
| 可审计证据 | 保存实际远端截图或录像、配置变化、逐阶段身份与版本；保留失败案例；增加截图泄密检测和连续运动场景 |
| 安全目标 | 如果目标是不受信任进程根本无法获取考试像素，需要操作系统级受支持能力或 Apple 明确提供的机制；本进程内后处理方案达不到该隔离目标 |

引用的 Apple 官方页面快照与获取时间保存在 [deployment-official](../research/deployment-official/manifest.json)。这些资料解释平台机制；本机的真实结论仍以对应实验文件为依据，不能用官方机制替代对具体厂商版本的验证。
