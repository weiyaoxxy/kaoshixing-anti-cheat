# 本机远程软件静态分析

记录时间（UTC）：2026-11-01T13:25:03.379642+00:00。本文件属于 Hook 新方案，独立于之前的受保护渲染 Demo。

## 结论与证据等级

**已验证的是磁盘二进制、签名配置、导入符号、框架依赖、当前进程身份和启动项；本文件不包含注入成功、实际取屏调用或远端遮蔽成功的证据。**

- ToDesk 5.2.3.0（build 2943）同时包含 ScreenCaptureKit、传统 CoreGraphics 单帧、CGDisplayStream 连续帧等静态线索。主程序、Service、Session、Screenwall Helper 和 zrtc 均需纳入候选范围。
- UU 4.40.0（build 621）的捕获实现优先候选是 libstreamer.dylib；主程序与 UURemoteServer 都链接该库，不能只看主程序是否直接导入 SCStream。libstreamer 同时具有 SCK 和 CGDisplayStream 线索。
- ToDesk 主要可执行组件声明允许 DYLD 环境变量、关闭 Library Validation 等例外，因此适合优先验证启动时加载；这只是实验条件，尚不等于可以附加任意既有进程或已经成功拦截。
- UU 检查到的主程序、Service、Daemon、Server 未声明上述例外。按默认加固规则，相同启动时加载方案存在明确障碍；应通过真实加载记录区分环境清除、库校验拒绝、未启动及未命中 API。
- 本机 SIP 读取结果：`System Integrity Protection status: enabled.` 本审计未改变它。

## 捕获入口静态线索

| 组件 | 静态线索 | 解释 |
|---|---|---|
| ToDesk / ToDesk_Service / ToDesk_Session / ToDesk_Screenwall_Helper | SCStream、SCContentFilter、SCShareableContent、SCScreenshotManager；CGDisplayStreamCreate/Start/Stop；CGWindowListCreateImage/FromArray；CGDisplayCreateImage | 至少存在多条编译进组件的候选路径，当前活动路径仍未知 |
| ToDesk zrtc.framework | SCStream；CGDisplayStreamCreate；传统 CG 单帧 | 共享媒体框架也可能承载实际调用；不能仅 hook GUI 自己的导入表 |
| ToDesk_Session_Proxy / ToDesk_XPCHelper | 未匹配到本脚本列出的捕获导入符号 | 不等于没有捕获能力，可能承担派生、IPC 或代理工作；也可能使用未纳入词表的路径 |
| UU libstreamer.dylib | SCStream、SCContentFilter、SCShareableContent；CGDisplayStreamCreateWithDispatchQueue/Start/Stop/UpdateGetRects | 重点候选媒体库；SCK 与 CGDisplayStream 应分别验证 |
| UURemoteServer | CGWindowListCreateImage；链接 libstreamer.dylib | 服务进程是优先观察候选，不代表已确认其当前正在取屏 |
| UU 主程序 | CGWindowListCreateImage；链接 libstreamer.dylib | GUI 也有直接或经共享库捕获的可能性 |

ToDesk 四个主要组件的限定字符串扫描还匹配到 `CGSHWCaptureWindowList`。这里只记录出现过该字符串，未确认它是可解析函数、是否执行、签名或捕获行为；不能据此认定私有后端，也不能将它列为已覆盖 hook。

扫描将 nm 未定义符号与 strings 命中分开保存在 JSON 中；只保留固定捕获 API/selector 词表的匹配项，不保存一般业务字符串、连接标识、密码或令牌。所有 34 个 Mach-O 均读取到 x86_64 与 arm64；本次词表匹配的未定义导入在两种架构之间没有差异。该结论只覆盖词表，不代表两套实现等价。

- [Debugger entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.debugger)：调试器权限并不允许获取任意受保护进程的 task port。

## 新方案应如何判定实验结果

1. 先取得 **库已加载** 的进程内日志，包含实际 PID、可执行路径、构建标识；缺少日志不能直接解释为某个保护机制拦截了加载。
2. 再取得 **目标 API 已调用** 的日志，区分进程启动后的真实捕获活动与实验代码主动调用的自检。
3. 再取得 **交付给捕获方的帧已改变** 的证据，同时保留普通可见内容正对照。
4. 最后由真实远端接收画面验证遮蔽与持续连接；库加载成功、API 替换成功不能代替远端结果。
5. SCK 连续流、CGDisplayStream 两类创建函数、传统 CG 单帧应独立记录；已有流、Helper 启动、重连和进程重启是另外的测试场景。

ToDesk 可先在不改签、不关闭 SIP 的条件下验证一个新启动的用户进程；若活动捕获实际上在现有 UID 0 服务，则应准确记录“用户进程 hook 不覆盖该服务”，不能把该实验扩展为 ToDesk 全面受控。UU 默认签名条件下的加载失败也应作为该方案的实测部署边界保留。

## 复现与范围

在本目录执行：

```bash
python3 scripts/audit-remote-targets.py
```

会更新本审计的 JSON 快照，仅使用 rg、lipo、otool、nm、strings、codesign、ps、sw_vers、csrutil status 等读取操作。脚本不加载目标代码，不附加目标进程，不启动或结束应用，不重签、注入、安装驱动或修改系统安全配置。此次审计只枚举两个 .app 内部；位于 /Library 的卸载辅助工具仅列出启动项路径，没有展开分析其二进制。
