# UU 继续推进：平台机制与厂商公开资料

查阅日期：2026-11-02。本轮仅查阅公开资料并整理已有实验，不启动、重启、注入或重签 UU，不联系厂商。

目前需要同时满足两个条件：**在真实采集进程中加载观测代码，以及让该进程继续参与正常的 UU 远控链路**。现有原签名组只满足后者；现有重签名副本只证明三个进程加载了 Hook，尚未获得采集调用或帧证据。Apple 文档支持这些条件彼此独立，但不能据此确定 UU 内部拒绝的具体规则。

结合[已有实际调用测试报告](../UU_Hook实际调用测试报告_20261102.md)，可形成以下研究判断：

- 原签名组远控正常但未加载 Hook，说明**当前加载路径没有成功**；零日志本身不能证明 UU 不调用任何已覆盖采集 API。
- 重签名组为三个进程、合计 48 条初始化/安装日志，均为 `loaded_only`；当轮未观察到副本 Server，亦无采集调用或帧证据。用户提供了钥匙串提示截图，没有明确反馈本轮是否离线。此前无 Hook 对照已提示副本改变了兼容/身份条件，但副本同时存在签名、entitlement、架构及元数据变化，不能把影响精确归因于签名单一变量。
- 33 次 IPC 拒绝及钥匙串请求是需要解释的关联现象，不足以确认唯一因果链。放行钥匙串提示也不能预先保证 IPC、Server 或采集链路恢复。
- 自有测试宿主已经证明观测代码可记录有效图像和帧；它不替代真实 UU 的端到端证据。

建议按以下关卡继续，当前仅提出方案：

1. **先做一次静态可行性盘点。** 基于现有产物，将 GUI、Service、Server、Daemon 的 DR、Team ID、Hardened Runtime 标志、entitlements、架构和加载位置列成同一张表；给每个拟采用加载路径写出必要前提。预先限定为一次盘点，不能由“不加载”升级成反复更改正式程序。
2. **加载路径关卡。** 优先厂商构建时加入观测代码，或厂商明确支持的 macOS 插件/调试构建；需要同套兼容的 GUI、Service、Server、Daemon 和独立测试授权环境。尚未取得接口或构建时，停止把“重签名副本+DYLD”当作生产可行路线，继续在自有宿主验证 API 覆盖即可。CLI 可用于状态编排，不能替代帧观测接口。厂商能力确认目前只列为后续待办，本轮不联系。
3. **工作链路关卡。** 将来获准测试后，先在隔离测试机器/账号中证明无 Hook 的整套构建可连接、显示动态测试图案并操作；然后保持同一构建与身份条件，只切换 audit 观测。设定单轮时间上限及独立恢复守护。Server 缺失、反复 IPC 拒绝、未知授权请求或恢复检查失败时，立即停止该轮并恢复，不用输入真实钥匙串凭据来试错。
4. **证据关卡。** 独立记录 session、PID、微秒出生时间、路径、签名和单调时间窗口；取得同生命周期映射、采集入口、成功图像/有效帧及原回调返回证据，并由远端独立确认动态画面和操作。仅 `loaded_only` 不进入“Hook 经过真实采集”的结论；只有帧回调也不宣称已经影响远端编码/显示。若要验证拦截效果，还需之后另行设计、授权和执行阻断对照。

可交付的下一阶段成果应先是“哪种受支持加载路径具备条件、哪些条件仍缺失”的可审查清单。当前资料没有支撑承诺“继续改注入参数即可让正式 UU 保持连接并经过 Hook”。
