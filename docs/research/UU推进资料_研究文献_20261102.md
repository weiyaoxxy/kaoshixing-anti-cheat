**UU 防护推进资料：研究文献与官方实现核对**

检索与阅读日期：2026-11-02。本文只整理公开资料和本工程已有代码，不操作 UU、不运行防护实验。以下区分来源结论、适用范围和工程推论；引用的网页、论文正文或源码均已实际打开阅读。源码固定到提交，避免以不断变化的 `main` 作为永久依据。

建议的主线是：先验证 macOS 原生考试模式能否满足限制目标，再完善服务端证据与异常处置；将 UU Hook 保留为特定版本的调用路径研究手段。考生拥有本机最高权限时，普通本地进程中的自检和日志只能提高发现概率，不能据此承诺“任何绕过都会留下可信证据”。这是下述信任模型与本工程现状共同得到的工程判断，并非文献已经测试过本项目。

**1. IETF RATS：把“上传日志”与“可信远程证明”分开**

作者：Henk Birkholz、Dave Thaler、Michael Richardson、Ned Smith、Wei Pan。年份：2023。标题：*Remote ATtestation procedureS (RATS) Architecture*，RFC 9334，Informational RFC，并非具体实现协议。

官方全文：[RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html)。实际阅读重点：§3、§7、§10.2、§12.1.1、§12.2。

来源结论：架构区分提供测量证据的 Attester、评估证据的 Verifier、据此决定是否授权的 Relying Party。测量环境和证明密钥应受到保护，不能被被测环境任意篡改；§12.1.1 特别讨论设备所有者不能修改或提取证明密钥的要求。验证方发出的不可预测 nonce 可以提供新鲜性依据，但不能单独保证测量真实，也不能完全消除测量与使用之间的时间差。[信任边界](https://www.rfc-editor.org/rfc/rfc9334.html#section-12.1.1)、[nonce 与新鲜性](https://www.rfc-editor.org/rfc/rfc9334.html#section-10.2)。

对本工程的推论：本地 `RuntimeIntegrityMonitor` 自检、UU 模块观察、哈希链、TLS 和签名上报可以分别解决部分篡改或传输问题；若测量器与签名调用都由考生控制的系统执行，它们仍不足以证明“所有报告都真实”。把 helper 提升为 root 也没有自动建立独立信任根。服务端应保存自己的接收时间、会话挑战、连续性及失联状态；客户端不能通过清空本机文件删除已经收到的记录，但仍可能伪造尚未上报的内容。

不适用点：RFC 没有提供可直接调用的 macOS TPM/运行时测量 API，也没有证明 Secure Enclave 密钥会自动测量 UU、dyld 或屏幕采集行为。硬件证明若要立项，必须先确定具体平台公开提供哪些 claims、验证方信任谁、是否覆盖运行中的考试进程，而不是仅增加一个“硬件签名”字段。

**2. Safe Exam Browser：macOS 的 AAC、进程监控与配置校验实践**

作者/维护者：Daniel R. Schneider、ETH Zurich IT Services 与 Safe Exam Browser 项目贡献者。年份：持续维护；本次于 2026-11-02 查阅发布说明和源码提交 `ba1b8ff2bd33d8951e04fe2d5151f47c16d0e8fe`，并核对旧版手册及开发文档。项目：*Safe Exam Browser for macOS and iOS*。

官方资料：[macOS 发布说明（本次页面首项为 3.7.1.1）](https://safeexambrowser.org/macosx/mac_release_notes_en.html)、[固定提交 README](https://github.com/SafeExamBrowser/seb-mac/blob/ba1b8ff2bd33d8951e04fe2d5151f47c16d0e8fe/README.md)、[固定提交 SEBController.m](https://github.com/SafeExamBrowser/seb-mac/blob/ba1b8ff2bd33d8951e04fe2d5151f47c16d0e8fe/Classes/SEBController.m)、[Config Key 开发文档](https://safeexambrowser.org/developer/seb-config-key.html)、[配置文件格式](https://safeexambrowser.org/developer/seb-file-format.html)、[SEB 2.3 旧版 macOS 手册](https://safeexambrowser.org/macosx/mac_usermanual_en.html)。

版本核对：旧手册最终 URL 仍为 `https://safeexambrowser.org/macosx/mac_usermanual_en.html`，本次读取为 578 行，正文标题明确写着“Safe Exam Browser 2.3 for macOS”。它确有 AAC 段落（网页提取行 414、502），不是缺少 AAC 的页面，但不能代表 3.7.x 的完整行为；本文将其限制为历史说明。当前 AAC 采用情况由 3.7 发布说明与上述固定提交源码支撑；JavaScript API 说明来自独立开发文档，不来自 2.3 手册。

来源结论与实现核对：

- 3.7 发布说明将 AAC 列为默认锁定模式，并通过 `lockdownModePolicy` 根据系统及配置选择模式。其 `screenProctoringAACCapturePolicy` 说明系统屏幕采集在 AAC 下输出黑色，SEB 因而采用自身视图采集；这是 SEB 官方对相应功能的说明，不能替代 UU 的实际测试。旧版 2.3 手册曾提示后台 daemon 可能自动重启，本文不以旧手册推定新版本完整行为。[3.7 发布说明及设置说明](https://safeexambrowser.org/macosx/mac_release_notes_en.html)。
- `SEBController.m` 的 `startProcessWatcher` 创建约 0.25 秒的检查定时器；`processWatcher` 检查禁止 BSD 进程，并将超过阈值的检查间隔作为可能暂停的信号。`assessmentSessionDidBeginWithCallback:` 等回调推进 AAC 状态。这里展示了持续检查及会话生命周期的实现方式，不能证明本地计时器不可被停止或篡改。[源码](https://github.com/SafeExamBrowser/seb-mac/blob/ba1b8ff2bd33d8951e04fe2d5151f47c16d0e8fe/Classes/SEBController.m)。
- Browser Exam Key 关联考试配置和应用代码签名；Config Key 主要校验配置。独立 Config Key 开发文档明确说明 macOS/iOS 3.0 及之后的 WKWebView 集成采用 JavaScript API；这项结论不来自 2.3 手册，且不能把该开发文档中的其他历史限制都当成当前版本状态。配置格式文档讨论密码/证书加密；这些概念不能统称为“每份配置都有服务端数字签名”，也不是对任意本机 root 的运行时证明。[BEK 历史说明（2.3 手册）](https://safeexambrowser.org/macosx/mac_usermanual_en.html)、[Config Key 与 JavaScript API](https://safeexambrowser.org/developer/seb-config-key.html)、[文件格式](https://safeexambrowser.org/developer/seb-file-format.html)。
- README 明确要求自行申请 Apple 的 `com.apple.developer.edu-assessment-mode` entitlement，并说明公开仓库不包含部分二进制安全模块。公开源码可供架构参考，不能当作可直接编译并继承全部产品安全能力的完整版本。[README](https://github.com/SafeExamBrowser/seb-mac/blob/ba1b8ff2bd33d8951e04fe2d5151f47c16d0e8fe/README.md)。

对本工程的推论：优先借鉴“系统考试模式 + 会话状态机 + 禁止进程补充检查 + 服务端配置校验”的分层。进程匹配应结合签名身份、实际路径和 PID 出生时间，不只依赖可变化的名称。睡眠、调度阻塞、权限不足和真正篡改需要分别记录；暂停/失联信号宜进入人工复核，而不是直接等同于作弊。

不适用点：SEB 的官方行为描述不是“UU 已在本机被 AAC 阻断”的实测证据；本次也没有执行 SEB。不能借 Windows 专属的 SEB Service、注册表或驱动机制断言 macOS 已获得对应能力。

**3. USENIX Security 2022：监考客户端的安全、隐私与误判需要一起验收**

作者：Ben Burgess、Avi Ginsberg、Edward W. Felten、Shaanan Cohney。年份：2022。标题：*Watching the watchers: bias and vulnerability in remote proctoring software*，31st USENIX Security Symposium，pp. 571–588。

官方链接：[论文介绍与书目信息](https://www.usenix.org/conference/usenixsecurity22/presentation/burgess)、[开放 PDF 正文](https://www.usenix.org/system/files/sec22-burgess.pdf)。实际阅读重点：研究范围与限制、§4 的客户端安全分析和考后监控问题，以及结论；印刷页 577 明确写明未研究 Mac 版本。

来源结论：研究分析四个面向法律教育/执业考试的监考套件，发现所研究版本中存在可绕过的客户端限制，以及用户安全和隐私风险。文中讨论了依赖进程/设备名称等列表检查的脆弱性，并指出高权限常驻服务在考试结束后的监控风险。研究没有评估这些产品的服务端组件，也明确没有调查 Mac 版本。[PDF](https://www.usenix.org/system/files/sec22-burgess.pdf)。

对本工程的推论：必须把“考试结束能否恢复”和“监控是否停止”纳入成功标准；新增权限/helper 时，应减少不必要的常驻面。记录最小必要的会话、签名/配置摘要、异常类型和覆盖缺口，默认不上传任意内存、密码、所有应用内容或画面。技术异常标记应与作弊认定分离，并提供复核记录。

不适用点：这篇论文不能证明当前 UU、当前 macOS、当前考试星或本工程已经存在其中某个具体漏洞；也不能把 2022 年被测版本的结果推广为所有监考软件永远无效。可借鉴的是威胁建模与验收方法，具体绕过需要在授权环境中单独验证。

**4. Apple 官方平台资料：新能力需要按 macOS 版本分支**

作者/发布者：Apple Education Technologies 团队（讲者自称 Chris）。年份：2026。标题：*What’s new in assessment on macOS*，WWDC26 Session 230。

官方链接：[视频、逐字稿和代码片段](https://developer.apple.com/videos/play/wwdc2026/230/)。实际阅读：Precondition checks、Application launch restrictions、Best practices。

来源结论：该场次针对 macOS 27，介绍要求 SIP、MDM 管理、单个登录账户与标准账户等前置检查，以及限制只运行参与考试的应用和必要系统进程。Apple 强调受限 AAC entitlement、通过状态回调判断真正开始/结束、只施加考试所需限制并测试新系统版本。[WWDC26](https://developer.apple.com/videos/play/wwdc2026/230/)。

对本工程的推论：若部署目标允许 macOS 27，可单独评估这些 API；若允许考生始终持有管理员/root 能力，就不能同时宣称已满足“标准账户且受管设备”这一更强前提。实现前须核验部署系统、SDK availability、签名 entitlement 与实际回调结果。旧系统需要独立能力矩阵，不能因为官网有接口就认为本机已经可以使用。

不适用点：这是平台设计与 API 说明，不是 UU 兼容性测试或独立安全评估。AAC 是否令 UU 离线、只阻断画面、恢复后何时重新连接，都需在原版 UU、正常连接基线下验证。

**对当前工程的落地建议（工程设计，尚未实现/验证）**

1. 明确产品保障等级：BYOD 管理员设备提供“限制常见路径并记录可见异常”；若考试要求更强保证，则要求受管设备、受限制账户或现场考试环境。不要仅靠增加客户端权限把两个等级混为一谈。
2. 独立验证 AAC：准备拥有正式签名和所需 entitlement 的最小样机，以会话回调作为状态依据。测试原版 UU 正常连接、考试开始、考试中重启 UU、异常退出/休眠、考试结束及恢复后重新连接，分别记录系统状态与远端人工观察。
3. 补齐服务端证据：服务端签发考试会话和配置策略；挑战与响应绑定会话、客户端版本/配置摘要和序号；服务端记录接收时间、异常事件、失联区间及结束确认。网络中断或权限不足标为覆盖不足，明确区分恢复、暂停考试和人工复核策略。哈希链只能暴露已知链上的破坏，不能使受控客户端产生的虚假内容变真。
4. 保留现有 Hook 的证据层级：模块加载、采集调用、有效画面帧、原回调返回、远端实际画面分别验收。任何一次注入导致 UU 离线，只能作为兼容性/干预结果，不能替代“连接正常时拦截采集”的证明。该项来自本项目已有实验设计，并非上述论文报告了 UU 行为。
5. 做发布版基线：当前 [RuntimeIntegrityMonitor.swift](../../Hook新方案_20261101/Sources/NativeExamDemo/RuntimeIntegrityMonitor.swift) 明确输出 `local_only_not_remote_attestation` 和 `serverReported: false`，未固定可信 Team ID 的开发构建保留未知状态；[构建脚本](../../Hook新方案_20261101/scripts/build-native-demo.sh) 默认 ad-hoc 签名。生产评估应固定发布身份和受信配置，但仍保留本地检测的可信边界。

本资料没有证明任何方案对 root 拥有者绝对不可绕过，也没有把本地检测失败当作作弊事实。下一阶段最有价值的验收成果是：一份按系统版本和签名条件列出的能力矩阵、一套完整恢复流程，以及能够明确呈现“已观察 / 未观察 / 无法确认”的服务端考试时间线。
