# UU 防护后续推进方案与资料综述

研究日期：2026-11-02。适用现状：本机 macOS 26.6.2 / Apple Silicon，SDK 26.5，UU 4.40.0（build 621）。本文是基于已有实验、Apple/UU 官方资料、公开实现与研究文献的工程方案；表中的后续能力均尚未完成实机验收。本轮仅查阅资料和代码、编写文档。

## 1. 推进结论

**建议并行推进两条线：产品主线完成“考试客户端异常检测、服务端记录、系统考试会话与恢复”；UU Hook 研究线先解决正常远控与受支持加载同时成立的条件。** 当前没有依据承诺继续调整注入参数就能解决正式 UU 的兼容问题。需要禁止远控时，直接评估系统考试模式比依赖重签名造成的失联更符合目标。

如果目标只是“检测自己的客户端是否被注入、发现 UU 是否加载了我们的 Hook”，现有模块已经具备部分观测能力，下一步是提高身份校验和证据可用性。如果目标升级为“考试期间持续阻止远控、考后恢复”，还需要独立的执行策略和会话状态管理。**发现库、发现采集调用、阻止远控、证明终端可信是四种不同能力。**

对拥有管理员/root 权限的考生电脑，可以提高常见绕过的成本、记录可见异常、在服务器记录失联；不能承诺任何绕过都一定被准确记录。普通本地日志、root helper、哈希链和 TLS 不会自动产生可信远程证明。更强保证应限定到受管理设备、受限制账户和已验证的平台安全前提。[RFC 9334 §12.1.1](https://www.rfc-editor.org/rfc/rfc9334.html#section-12.1.1)

## 2. 现有实验确定了什么

| 条件 | 已确认的事实 | 仍缺少的证据 |
| --- | --- | --- |
| 正式 UU + audit 环境加载尝试 | 远端画面与操作正常；实际映射没有本库；无 Hook 日志 | 正式采集进程加载观测代码 |
| 既有重签副本 + audit | Service 与两个 GUI 加载库；合计 3 次加载、45 次安装事件 | 正常远端会话；采集调用；有效帧；本轮快照未见副本 Server |
| 同一重签阶段的诊断 | 钥匙串授权请求；原 Daemon 33 次 IPC listener reject | 拒绝的精确规则和唯一原因；不能认定批准钥匙串即可解决 |
| 自有宿主控制组 | 6/6 集成测试、47/47 分析器测试通过 | 不能替代真实 UU 的采集/传输/显示链路 |
| 恢复正式环境 | 用户确认远控正常；拒绝后钥匙串弹窗消失 | 不等于产品已实现考试结束自动恢复 |

证据见[实际调用报告](UU_Hook实际调用测试报告_20261102.md)和[更早的签名/Hook 对照](UU签名与Hook对照实验_20261102.md)。旧对照中重签副本不加载 Hook 也无法连接，说明 Hook 并非该副本失联的必要条件；副本还有权限、架构等变化，不能把差异精确归结为签名单一变量。本轮重签阶段没有新的“设备离线”用户确认，不能沿用旧反馈填补证据。

Apple 对宿主 DYLD 环境许可和库验证的说明，与原签名组不加载的现象一致；代码身份改变也可能影响钥匙串及 IPC 信任。它们解释了合理方向，尚未揭示 UU 内部规则。[DYLD 许可](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-dyld-environment-variables)、[库验证](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)、[签名要求 TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)

## 3. 资料带来的路线选择

| 路线 | 能解决的问题 | 前提、版本与边界 | 建议 |
| --- | --- | --- | --- |
| 自身完整性检测 + UU 只读观察 | 发现已覆盖的模块、签名、关键方法变化；显示读取失败 | 自检可被有能力的对手干扰；模块名称命中不等于库身份可信；无映射不等于无任何 Hook | 立即完善 |
| 服务端会话与证据接收 | 保留已经收到的事件；识别重放、缺号和失联区间 | 不能把伪造的客户端测量变真；断网不等于作弊 | 立即建设最小闭环 |
| AAC 系统考试模式 | 在考试会话内限制系统功能，减少依赖逐个远控产品的 Hook | Apple 受限 entitlement；必须等生命周期回调；本机需真实验证 UU | 首选防护候选 |
| Endpoint Security（ES） | 根据进程身份拒绝新的执行，并记录执行事件 | 受限 entitlement、FDA；系统扩展还需部署批准；不能自动终止已建立的远控会话 | AAC 留有明确缺口时再引入 |
| SMAppService 后台组件 | 正规注册必要的特权操作和独立恢复逻辑 | LaunchDaemon 需管理员批准；不使普通 helper 获得不可停用保证 | 按实际需要添加 |
| 受支持的 UU 插桩/插件 | 验证真实 UU 采集路径，研究可控帧处理 | 需兼容的整套构建或明确 macOS 接口；当前未取得 | 限定条件的研究分支 |
| MDM + 受管设备 | 统一部署策略、账户与系统扩展条件 | 不适用于未纳管的任意个人电脑；系统远程设置不等于全部第三方远控路径 | 高保障场景单独方案 |

AAC 官方列出的 Mac 限制包括屏幕共享/镜像、截图/捕获和 Remote Login；这支持开展验证，**不是 UU 所有版本、所有既有会话必定断开的保证**。验收应观察试题是否泄露，并分别记录连接、帧、输入行为。[Apple 考试模式说明](https://support.apple.com/en-us/101976)

### 必须保留的版本分界

| 本机可以规划验证的能力 | macOS 27 才能另行验证的能力 |
| --- | --- |
| 已有 AAC 会话、参与应用配置；26.1+ 的 `allowsScreenshots` 仅涉及剪贴板截图 | `allowsOnlyParticipantsToRun`、`requiresSIP` 等新的配置项；Mac App Attest 支持 |
| 本机 26.6.2、SDK 26.5，不代表已经获得 AAC 授权 | 必须有匹配系统/SDK、签名及硬件支持，先检查 availability / `isSupported` |

没有查到通用的 AAC `allowsScreenCapture` 属性。`allowsScreenshots` 不是录屏或远控白名单，不应据此承诺“自己的监考程序可录全屏，其他软件不能录”。自有渲染帧录像需要单独验证。[截图属性](https://developer.apple.com/documentation/automaticassessmentconfiguration/aeassessmentconfiguration/allowsscreenshots)

macOS 27 的参与进程限制值得评估，但 **Apple 对 `requiresSIP` 明确说明：用户有管理员权限时检查可能不可靠，也不能判断 SIP 曾关闭期间是否发生修改**。App Attest 提供另一种服务端验证依据，仍不证明所有运行行为；当前资料未确认全部 Mac 分发渠道组合，不能列为本机马上可用的功能。[参与进程属性](https://developer.apple.com/documentation/automaticassessmentconfiguration/aeassessmentconfiguration/allowsonlyparticipantstorun)、[requiresSIP 限制](https://developer.apple.com/documentation/automaticassessmentconfiguration/aeassessmentconfiguration/requiressip)、[App Attest WWDC26](https://developer.apple.com/videos/play/wwdc2026/201/)

## 4. 推荐实施顺序与交付物

以下工作量是单名熟悉项目的 macOS 工程师的初步估算，不是排期承诺；不含 Apple 授权、证书准备、厂商响应或多机测试资源等待。

| 阶段 | 工作内容 | 交付与进入下一阶段的条件 | 初估 |
| --- | --- | --- | --- |
| P0：能力与身份基线 | 固定目标系统、UU/客户端版本、发布签名；列出四类 UU 组件的角色、签名、架构、权限、可读取程度；划分 BYOD/受管目标 | `capability-manifest`；开发 ad-hoc 身份仍为 unknown；不把缺权限标成通过 | 1–2 天 |
| P1：检测与服务端闭环 | 复用现有两个 Monitor；增加会话、策略摘要、事件上传、接收确认、失联处置；完善考试与恢复状态机 | 自身异常、UU 观察、覆盖不足在服务端时间线上可区分；模拟断网/重放/崩溃通过 | 3–5 天 |
| P2：最小 AAC 样机 | 将现有参考生命周期接到受许可的签名测试 App；系统会话与试题显示绑定；测原版 UU | 已连接、新连接、重启 UU、正常结束、异常退出均有真实远端记录；失败状态不继续展示试题 | 获授权后 3–5 天 |
| P3：按缺口评估 ES | 若仍需阻止重新执行，原型验证 AUTH_EXEC、身份匹配、存量进程和恢复租约 | 明确事件覆盖和失效行为；重启/超时/撤销权限不被误记为有效防护 | 获授权后 5–10 天 |
| R：UU 调用研究 | 核实厂商支持路径；拿到兼容测试构建后按第 5 节逐关验证 | 只有正常远控与真实采集日志同时成立，才进入帧处理研究 | 静态盘点 1–2 天；外部依赖无法估时 |

**首个里程碑取 P0 + P1：发布身份、服务端异常记录、考试与恢复状态机。** AAC 授权资料可并行准备；没有 entitlement 时只能验证代码和模拟转换，不能标成系统限制已生效。ES 不应成为默认必装项：若目标系统的 AAC 已满足需求，应避免重复引入高权限组件。

### P1 的具体代码落点

| 现有文件/拟新增模块 | 具体改动 | 可审查验收 |
| --- | --- | --- |
| `RuntimeIntegrityMonitor.swift`、`build-native-demo.sh` | 发布构建固定本方 Team ID / bundle identity，核验 Hardened Runtime 与实际 entitlements；区分观测异常和允许的组件 | 发布身份正确通过；篡改/未知身份按规则标记；现有开发构建不伪装发布版 |
| `UUHookMonitor.swift` | 保留每个角色/PID 出生身份、读取覆盖和 unknown；将本库文件身份与文件名线索分开；身份校验不能误称内存测量 | 不只看 GUI；Server/Daemon 读不到明确 unknown；重命名、PID 复用和权限不足不产生“已拦截” |
| 拟新增 `ExamSessionCoordinator.swift` | 统一准备、启动中、考试中、保护失效、结束中、恢复中、恢复完成/失败状态 | 只有所选防护配置的必要条件满足才开始；结束回调迟到、重复结束、开始中取消均可处理 |
| 拟新增 `ExamEvidenceClient.swift` 与测试接收端 | 会话绑定事件、去重重试、服务端确认、独立时间线、失联策略 | 重放和跨会话事件被拒；断网后补报保留发生与接收时间；服务器明确标注客户端自报 |
| 拟新增 `RecoveryCoordinator` | 记录本次确实改变的项目；幂等撤销；必要策略有独立到期机制；下次启动修复未完成事务 | 恢复组件和原始状态仍可用时，正常结束与进程被终止两条路径均完成回滚；组件被禁用/移除时标记恢复未确认并提供人工恢复路径 |

代码入口位于 [NativeExamDemo](../Hook新方案_20261101/Sources/NativeExamDemo/)；[AAC 参考代码](../Sources/AssessmentSessionExample.swift.txt) 当前明确不参与可运行 Demo 构建。[entitlements 示例](../Sources/AssessmentSessionExample.entitlements.plist) 不代表 Apple 授权已取得。现有客户端自检仍标记本地证据，UU 模块仍将 `actualHookInvocationVerified` 和 `captureBlockingVerified` 保持为 false，不能因自有宿主测试通过而改成 true。

最小证据字段建议为：考试会话 ID、实例 ID、事件序号、策略/客户端版本摘要、角色与进程生命周期、检查类型、结果、无法检查的原因、客户端单调时间；服务端另存接收时间、挑战、确认序号和失联区间。仅为设备兼容诊断所需的信息才增加采集。

服务端可以试行“每 5 秒心跳、连续 3 次缺失进入覆盖不足”的起始参数，但须用实际延迟、休眠和网络测试校准。心跳缺失触发的状态是待复核/暂停后续出题，不能直接定性作弊；服务端停止发新题也不能撤回已在客户端显示的数据。

## 5. UU Hook 研究线如何继续

### R0：一次性核对四组件身份

基于现有证据，补齐 GUI / Service / Server / Daemon 的路径、DR、Team ID、权限、架构和运行关系。避免把所有 GUI 都手动启动造成重复实例。先找出真实采集宿主；没有观测到 Server 或无法读取 root 组件时，保留未知，不拿 GUI 的初始化日志顶替。

只提高检查器权限不代表能向 Hardened Runtime 目标加载代码；调试工具 entitlement 也不等于任意目标可调试。[Apple 调试权限说明](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.debugger)

### R1：先取得正常且可插桩的工作条件

优先条件为厂商将观测代码纳入其构建、提供兼容的整套调试构建，或确认支持的 macOS 插件/采集接口。需要核实配套 GUI/Service/Server/Daemon 的互信、测试账户、适用版本和恢复方法；仅换测试 macOS 用户不能消除机器级 Daemon 的身份检查。

UU 公开资料确有 CLI 和运维版插件线索，但目前查到的新版 CLI 契约/运维教程针对 Windows，不能直接套到 Mac；未找到公开的 Mac 帧 SDK 契约，不代表私有合作接口不存在。[UU CLI](https://uuyc.163.com/help/cli.html)、[运维版教程](https://uuyc.163.com/help/ops.html)

后续拟向厂商确认的问题：Mac 是否支持采集观测/过滤接口；是否可提供与后台组件配套的测试构建；身份、钥匙串和 IPC 的支持要求；哪些诊断字段可判断会话与采集状态；更新后兼容承诺。这里只准备问题清单，本轮没有联系厂商。

**停止条件：** 没有可验证的受支持加载前提，不再重复相同“重签副本 + DYLD”实验；继续用自有宿主验证日志和 API 覆盖。关闭 SIP、修改厂商身份检查或依赖登录故障，不进入产品部署方案。

### R2：有条件后做严格对照

在专用测试 Mac 和测试账号上，先证明整套构建在无观测代码时可远控，再只切换 audit。保持组件版本、签名条件、架构、权限、启动路径一致；如无法保持，要明确剩余变量，不能称为单变量因果证明。单轮限时、独立恢复，避免用个人钥匙串凭据反复试错。

| 顺序 | 样本与观测 | 通过条件 |
| --- | --- | --- |
| A | 同套无观测构建；动态编号测试窗口 | 远端连续看到编号变化，输入返回可核对；无异常 IPC/授权障碍 |
| B | 同套 audit；独立记录进程出生身份、时间窗及映射 | 真正采集宿主加载本库，出现采集入口、有效帧和原回调返回；远端仍正常 |
| C | 后续独立验证遮蔽/阻断策略 | 远端对照确认试题区域达到明确目标；连接状态、非试题区域和本地操作分别记录 |
| D | 撤销实验、恢复 | 正式程序及启动定义与基线一致，原版远端画面/输入正常，无遗留授权弹窗 |

B 之前只得到 `loaded_only` 就停止推进帧效果结论。只有 B 的证据成立，才能说“正常工作的 UU 采集调用经过我们的代码”；C 才能说明远端实际防护效果。采用现有 [v1.3 日志和严格分析器](../Hook新方案_20261101/scripts/analyze-hook-invocations.README.md)，另补独立远端证据以及日志终点确认。库内的“回调已返回”不等于帧已经编码、传输或显示。

## 6. 考试期间阻断与考后恢复怎样验收

使用原版 UU、真实第二台控制设备和含持续编号的测试窗口。除特别测试故障外，每轮先确认正常连接；每项保留会话策略、组件身份、事件和远端观察，不用进程存在或 CLI 返回成功代替端到端结果。

| 场景 | 必须记录 | 通过标准/处置 |
| --- | --- | --- |
| 进入考试前已有 UU 连接 | AAC 开始回调、最后可见编号、输入状态 | 考试内容出现前所选限制已生效；若验证不满足则不开始 |
| 考试中发起新连接 | 连接结果、是否取到试题、输入是否生效 | 按产品目标阻止试题泄露或远控；明确实际机制而非统称“离线” |
| 考试中重新打开 GUI/Service/Server | 新生命周期、是否自动重启、策略状态 | 覆盖重启后的路径；仅一次 kill 不算持续阻断 |
| 本地检测被暂停/结束、权限被撤销 | 可见的本地事件、后台状态、服务端失联 | 标记保护不足并按规则停止继续考试；不保证一定辨识为恶意操作 |
| 断网、睡眠、系统忙 | 时间窗、重连、序号连续性 | 与篡改证据分开；恢复后重新验证必要条件 |
| 正常交卷/取消 | 隐藏试题、结束回调、撤销本次策略 | 恢复后原版 UU 可再次连接、显示动态画面及操作 |
| 崩溃、强制退出、注销、重启 | 独立恢复/到期记录、下次启动修复、服务端中断 | 恢复组件和原始状态可用时完成回滚；否则标记恢复未确认并提供人工恢复；考试按中断处理 |
| 管理员操作、文件副本、改名、旧版本 | 签名/身份与覆盖差异 | 不只按名字匹配；说明哪些路径支持、哪些无法确认 |

恢复应撤销考试临时策略并恢复此前确实改变的状态。若产品需重启考试前已运行的 UU，应核对路径和厂商身份后实现；不能承诺自动恢复之前的远控连接、账户授权或未保存工作。独立恢复组件提高异常退出时的可靠性，但不保证在管理员删除全部相关组件后仍能执行。AAC `didEnd`、策略解除、UU 再次连接成功是三个独立验收结果。[AAC 会话生命周期](https://developer.apple.com/documentation/automaticassessmentconfiguration/aeassessmentsession)

若采用 ES，AUTH_EXEC 只覆盖新的执行；已有会话必须单独处理。授权回应应在本地及时完成，不能依赖实时云端查询。Apple WWDC20 说明超时有客户端终止及隐式放行行为，目标系统必须复核与压测。ES 系统扩展的 SIP/服务保护也不能移植为普通 root helper 的能力承诺。[Endpoint Security 官方讲解](https://developer.apple.com/videos/play/wwdc2020/10159/)

## 7. 怎样给异常分级

| 展示给审核人员的结果 | 所需依据 | 不应写成 |
| --- | --- | --- |
| 检测到客户端完整性异常 | 有效身份检查失败，或受监测方法/模块出现不符合策略的变化 | 已确认考生作弊 |
| 观察到已知 Hook 模块 | 同一进程生命周期中的映射证据，附库身份核验程度 | UU 的取屏已被拦截 |
| 已验证真实采集调用经过观测代码 | 匹配身份/会话的有效调用和帧链，且真实远控对照成立 | 所有截图路径永久受控 |
| 检查覆盖不足 | 权限不足、进程切换、超时、日志缺口或服务端失联 | 没有 Hook / 检查通过 |
| 本次已检查项未发现异常 | 指明版本、时间窗、检查覆盖和信任条件 | 对方无法绕过 |

服务端独立保存已收到的证据，可以防止“删除本机日志就抹除历史”。挑战和序号有助于发现重放/断档，但不能阻止有充分控制权的客户端为当前挑战构造虚假测量。App Attest 可作为 macOS 27 分支研究的增强证据，仍须限制声明范围。[RFC 新鲜性模型](https://www.rfc-editor.org/rfc/rfc9334.html#section-10.2)、[Apple App Attest](https://developer.apple.com/videos/play/wwdc2026/201/)

## 9. 下一阶段的完成定义

第一阶段交付应是：一份真实能力清单、一套可演示的考试状态机、一条服务端异常时间线，以及正常结束/异常结束均可审查的恢复记录。没有 Apple 授权时，AAC 状态明确显示尚未验证；没有兼容 UU 工作条件时，真实调用状态维持未验证。这样现有检测工作可以先落地，系统防护和 UU 研究也各有可测的继续条件。
