## 结论

**本轮没有获得“正常远程连接中的 UU 采集调用经过我们的 Hook”的证据。** 已完成实际 UU 的原厂签名加载尝试、现有重签副本 audit 实验、调用日志分析和恢复验收。两个条件分别停在不同阶段：原厂签名 UU 能正常连接但未加载本库；重签副本成功加载并安装 Hook，但出现钥匙串凭据授权请求和 IPC 拒绝，没有记录到采集入口或有效帧，未完成正常远端会话验证。

**检测工具自身验证通过：6/6 个自有宿主集成测试、47/47 个分析器单测，无跳过。** 自有宿主结果不能替代真实 UU 验证，也没有证明考试画面遮蔽成功。

**已恢复正式 UU。** 用户确认连接正常；遗留钥匙串弹窗经用户点击“拒绝”后消失。正式用户 Service / GUI / Server 均无已知 Hook，原启动定义和程序哈希与基线一致，两个恢复守护已退出。

## 限制与后续条件

1. 当前未构造出“UU 连接正常且实际采集进程已加载 Hook”的条件，因此真实 UU 调用命中与画面遮蔽均不得标为通过。
2. 本轮两个阶段均观察到两个 GUI 实例（自动启动及显式启动），属于启动方式的限制，不是严格单变量比较。现有重签副本还包含此前的签名、权限和架构变化；不能只归因于某一字节签名差异。
3. 0 次调用是本次已覆盖、已记录路径的观测，不证明 UU 从未通过任何其他 API 捕获。日志有采样，缺少独立最终序号；本地文件及清单也不具备防篡改可信证明。
4. 自有测试只验证调用记录、有效帧识别、原回调返回及功能回归；未做像素逐字节一致性、真实远端编码/传输/显示或遮蔽验收。
5. 后续需要能正常连线且允许受支持插桩的 UU 环境，例如厂商支持的调试构建/集成方式。先验证捕获宿主正常连线，再继续真实帧的 audit 验收；不能用离线或授权失败替代防护成功。
