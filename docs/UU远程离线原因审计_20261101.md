# UU 远程离线原因审计

审计日期：2026-11-01。本文时间统一使用 Asia/Calcutta（UTC+05:30）；原始 JSON 中的时间为 UTC。

**2026-11-02 更正与后续验证：** 已实际重启原版 GUI、用户 Service 和 Server，并完成本机检查。发现 UU 的辅助功能树包含隐藏的错误标签，原审计仅根据 AX 文本判断“界面仍显示 1001”的证据不足；该判断已更正。历史实验期间的 IPC 拒绝和用户无法连接反馈仍然成立。当前可见窗口、官方 CLI 及最终进程检查见 [恢复验证报告](UU远程恢复验证_20261102.md)；用户暂时无法配合另一台设备连入，尚未完成端到端验收。

**同日后续闭环：** 用户随后确认原版可连接，并授权重启旧实验设置复测；三阶段远端结果为“可连接 → 无法连接/离线 → 恢复后画面和操作正常”。[复测报告](UU远程阻断复测_20261102.md)确认旧实验组合配置是本轮故障的可复现触发条件；具体签名/注入因素仍未分离。

## 结论

**项目中的 UU 副本实验确实替换过本机正在使用的正式后台服务，实验期间出现了进程间连接被拒绝，以及用户确认的“无法连接或设备显示离线”。它是有运行证据支持的故障诱因。** 不能把该实验理解成只在项目文件夹里运行、不会影响正式 UU 的独立测试。

**当时原版服务已重新运行，未发现实验副本进程或 Hook 库仍在当前 UU 进程中；辅助功能树包含“无法连接至服务器”“错误码：1001，请检查网络配置”“正在连接”。这些标签当时未做可见性核验，不能单独证明应用仍处于连接失败状态。** 本次没有取得平台登录/注册失败的底层业务日志，不能断言用户报告的离线全部由此前实验造成，也不能把“原启动配置恢复”当作“远程连接已恢复”。

本轮进行了源码、历史实验产物、当前进程/启动配置/签名、系统日志、网络配置及应用界面的只读检查。未重新执行实验，未修改 UU 配置、权限或签名，未重启或结束 UU 进程。新增文件仅为审计报告和脱敏证据。

## 代码发现

### 1. 高优先级：所谓副本实验直接占用正式服务

[uu-copy-service-experiment.py](../Hook新方案_20261101/UU深入验证_20261101/scripts/uu-copy-service-experiment.py)：

- 31–35 行固定正式服务标签 `com.netease.uuremote.agent` 与原版/副本路径。
- 281 行把启动程序替换成副本；285–286 行添加 `DYLD_INSERT_LIBRARIES` 和 Hook 环境变量。
- 314 行卸载当前用户正式服务，328 行以原标签注册实验服务。
- 279–280 行说明保留原 MachServices 和 WorkingDirectory。原版与副本的 bundle ID 都是 `com.netease.uuremote`，并非完整隔离的应用环境。

因此，即使 `/Applications/UURemote.app` 和 `/Library` 中的原 plist 字节未改动，正在运行的服务仍会被替换。这足以中断原有连接。系统日志中的 peer 拒绝进一步证明实验期间出现了实际通信异常。

拒绝日志没有给出具体被拒绝的 peer 身份或原因。副本重签名与原版组件之间的身份校验不兼容是合理怀疑，**尚不能定论为某项具体签名校验失败**。

### 2. 高优先级：恢复条件只检查注册身份，没有检查可用性

同一脚本 202–231 行：

- 223 行调用 `wait_for(dom, SOURCE, PROGRAM)`，没有要求 `require_running=True`。
- 224 行只用路径与程序身份判断恢复；226 行即设置 `status='restored'`。
- 229 行记录进程快照，但不清理或阻止遗留副本 Server；230 行明确说明不声称远程功能恢复。

本次实际快照恰好印证这个缺口：任务仍是 `xpcproxy` 时已标记恢复，同时仍有副本 Server。**这是当时的恢复缺口；本轮检查未再发现该副本进程，不能写成“当前仍有副本残留”。**

后续应把“原定义已注册”“正式进程已运行”“副本进程已退出”“客户端已上线”“远端连接成功”分别记录。未完成后两项时，不应在面向使用者的说明里声称服务已恢复正常。

### 3. 中优先级：加载验证入口会退出并重新启动正式 GUI

[test-uu-load-witness.py](../Hook新方案_20261101/scripts/test-uu-load-witness.py) 的 26 行请求退出正式 GUI，36 行必要时发送 SIGTERM，48–51 行带加载实验环境启动正式 GUI；脚本没有 `finally` 将 GUI 正常重启恢复。[验证UU加载限制.command](../Hook新方案_20261101/验证UU加载限制.command) 直接调用该脚本。

这是另一个可能中断正常使用的入口。但早一轮测试后已有 20:11 的正常连接确认，所以最近 21:20 的服务副本实验与本次故障的关联更强。

## 本轮检查排除或缩小了哪些范围

- **正式应用完整性：** `codesign --verify --deep --strict --verbose=2 /Applications/UURemote.app` 成功，版本为 4.40.0（621）。原启动 plist SHA-256 与本轮实验保存的原版备份一致。
- **当前启动项：** `gui/501/com.netease.uuremote.agent` 为 `running`，程序路径是 `/Applications/UURemote.app/Contents/MacOS/UURemoteService`。没有 `DYLD_INSERT_LIBRARIES` 或 `HOOK_DEMO_*` 环境键；用户级全局 DYLD/Hook 模式查询为空。
- **当前进程：** 正式 GUI 47130、Service 50205、Server 50360；`vmmap` 检查没有 `libCaptureHook` 或 `libLoadWitness`。当前进程列表未见项目副本。
- **被控开关：** `/Users/Shared/UURemote/Shared/pub/setting.config` 的 `controllable`、`assisted`、`auto_launch` 均为 true。该文件修改时间位于实验期间，但没有实验前的内容备份，不能仅凭时间认定是谁修改了什么。
- **网络配置：** macOS 应用防火墙关闭、block-all 关闭；系统 HTTP/HTTPS/SOCKS/PAC 代理均未启用；UU `proxy.config` 为空。默认路由经 `en0`，系统可达性显示 Reachable；当前 Server 存在一条已建立的 TCP 443 连接。这些不等于 UU 所需全部服务都可达。
- **源码范围：** 未发现项目代码写入防火墙、DNS、hosts、全局代理、TCC 或全局 `launchctl setenv` 的操作。ToDesk 脚本限定自己的服务标签，未找到误操作 UU 的路径。这个结论不能排除项目之外的历史手动命令，也不能排除实验运行的 UU 自身写入共享配置。
- **Hook 行为：** 本轮副本实验为 `audit` 模式，仍安装进程内 Hook；已有记录只有库加载/安装事件，没有有效远程捕获验证，不能把离线当作“防截屏生效”。

## 当前仍不确定的部分与恢复顺序

正式组件恢复后的 IPC 端点创建与 HTTP 200，只能证明部分通信已经发生，不能证明业务握手、设备上线或远端连接成功。当前业务日志使用二进制 `.xlog/.slog`，本轮未解码，因此没有得到用户所述故障对应的底层注册/鉴权/连接错误。辅助功能树中的 1001 不是独立的连接失败证据。

下一步应先完整重启原版 UU 的 GUI 及当前用户 Service/Server，再检查 1001 是否消失、设备是否上线，并由另一端重试。操作时应核对实际进程路径，避免再次启动项目里的测试副本。无需根据现有证据先重置全局网络、防火墙或隐私权限。

如果完整重启后仍为 1001，再通过 UU 自带诊断取得业务错误，并对所需服务器逐项检查。当前证据不足以选择“网络不可达”“平台注册/鉴权失败”或“实验后的共享状态异常”中的唯一原因。此次审计没有进行这些恢复操作，也没有宣称问题已修复。
