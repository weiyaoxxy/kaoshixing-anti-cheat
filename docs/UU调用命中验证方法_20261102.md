# 如何验证 UU 的实际采集调用经过 Hook

要证明当前 UU 的采集流程经过我们的代码，必须先让“已加载 Hook 的真实采集进程”仍能建立正常远程连接，再把本次进程身份、会话时间窗、具体调用、有效帧及原回调返回关联起来。日志字符串、库加载或安装成功本身不足以说明发生了实际采集。

## 当前结果与关键前提

已升级 `CaptureHook.m` 为 v1.3 / schema 2，构建 `build/libCaptureHook-v1.3.dylib`；新增严格调用分析器和自有窗口的真实集成测试。没有对 UU 加载库、重签、重启或调整配置；GUI 原有 `actualHookInvocationVerified` 不会因为自有宿主通过而变成 true。

**真实 UU 仍未验证调用命中。** 之前保留原厂签名的副本可以连接；现有重签副本即使不加载 Hook 也离线。因此现有重签副本不能用作“连接正常时采集实际经过 Hook”的验证环境。既有原版 DYLD 加载方式未成功，原版组件启用了 Hardened Runtime；需要先找到与正常连接兼容的加载方式，例如厂商提供的受支持调试构建/扩展方式，或后续另行验证的兼容实验环境。不能通过关闭系统保护或把离线当成功来跳过这个前提。

此前连接时运行栈已指向 `UURemoteServer` 的 ScreenCaptureKit 帧处理路径，因此应优先匹配 Server 的采集证据，而不是只看 GUI。其他进程若确实有调用，也应单独记录身份与证据，不能把进程名称当可信证明。

## 本次新增的支撑

| 支撑 | 用途 |
| --- | --- |
| sessionID、Hook实例UUID、PID、微秒级进程出生时间、可执行路径 | 拒绝旧会话、旧进程或 PID 重用的日志 |
| 锁内序号、单调时钟、每 PID 日志、写入失败计数 | 发现序列缺口、可检测截断与损坏；不能保证本地文件未被人为修改 |
| callID / api / operation | 区分真正截图或 startCapture 入口，与 init、添加输出、更新、停止 |
| 截图结果关联 | 将实际有效图像/样本和错误关联回原请求 |
| streamID / outputID / frameID | 将创建、设置、开始、帧和回调返回关联到同一采集流 |
| validScreenFrame 与独立有效帧计数 | 排除 idle、blank、缺失状态、未 ready、空图和非屏幕样本；确保首次有效帧被记录 |
| frame_forwarded | 记录同一帧的原 handler/delegate 已返回；不证明已经编码、传输或远端显示 |
| 外部期望清单及分析器 | 要求独立记录会话、进程和时间窗，严格分析已结束实验的日志 |

旧格式日志保留历史价值，但不能升级成 schema 2 的当前调用证据。日志仍属于本机可修改材料，不能替代服务端存证或远程证明。没有独立最终序号时，删除尾部完整记录无法仅凭剩余日志发现。

## UU 正式实测步骤

1. **正常连接基线。** 原版 UU 无 Hook 时，由另一台设备连接。记录时间和 GUI / Service / Server / Daemon 的 PID、启动身份；确认原生考试测试窗可见、动态文字更新且输入操作正常。
2. **建立兼容的 audit 环境。** 必须先确认加载 Hook 后仍能连接，不修改返回画面；使用新会话 ID 和每 PID 的新日志。加载位置要覆盖真正采集的进程。若只得到离线、崩溃或加载失败，本轮到此为止，结论是无法验证实际采集，不能判保护成功。
3. **触发真实取屏。** 远端连接后，在本机合成考试窗内持续修改文字、滚动或移动窗口约 20–30 秒。记录远端连接正常的观察时间窗，采集原回调证据，不把开发测试宿主混入 UU 清单。
4. **结束窗口并分析。** 封存日志和由控制器独立产生的期望清单，核验当前 UU 进程实际加载的库路径/版本。运行分析器，检查身份和时间窗全部匹配、`evidenceUsable=true`；SCStream 应观察到对应创建/设置/start、有效屏幕帧与同一 frameID 的原回调返回。单独 `capture_entry_observed` 只说明入口走过，API 可能失败，仍不等于有画面。
5. **复测和恢复。** 断开/重新连接时分别记录观察窗口；进程重启后必须使用新出生身份和新日志，不能复用旧 green 状态。停止后可能仍有已排队回调，不能要求停止请求后立刻零事件。测试结束核验正式环境恢复并由远端确认正常。

要证明画面遮蔽，再单独做 block 对照：考试区不可读、公共动态区域仍更新、远端操作与连接正常、停用后恢复。调用和帧日志不能代替这一层。

## 可立即运行的自有宿主测试

在 `Hook新方案_20261101` 目录：

```bash
bash scripts/build-hook.sh "$PWD/build/libCaptureHook-v1.3.dylib"
python3 scripts/test-hook-invocations.py --dylib "$PWD/build/libCaptureHook-v1.3.dylib"
```

测试只创建自己的合成文字窗口，只采该窗口，不保存图片、不请求新权限、不操作 UU。若录屏权限预检不通过，会跳过实际捕获并明确记录，不能报告帧已通过。

本机 6 个集成用例全部通过：无 Hook/有 Hook 的纯加载、真实单窗口截图与屏幕流、同一输出对象移除音频后保留屏幕流。audit 纯加载准确输出 `loaded_only`；audit 两种采集用例均为 `frame_callback_observed`，实际宿主各收到了 1 张有效截图和 2 个完整屏幕帧，原回调返回证据通过。baseline 也分别得到有效截图及帧；这是功能结果核验，不是逐像素一致性或防遮蔽验证。

分析器 47 个用例通过，覆盖旧格式、错会话、PID 重用、时窗不符、断序、截断、仅初始化、失败截图、空闲/错误帧、setup失败、重复输出、并发回调排序和缺失关联。另以 8 个自有进程并发写共享文件验证 JSON 不被交叉写坏；竞争产生的日志缺失明确可见，推荐独立 `%p` 日志。
