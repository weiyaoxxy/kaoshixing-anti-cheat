# UU 远程恢复验证

日期：2026-11-02。时间使用 Asia/Calcutta（UTC+05:30），证据 JSON 使用 UTC。

**后续补充：** 用户随后明确确认别人已经能通过 UU 连接，见 [人工连通反馈](../artifacts/uu-recovery-validation-20261102/07-human-remote-connected.json)。随后经用户授权，又完成“正常 → 启用旧设置后无法连接 → 恢复后画面和操作正常”的完整复测，见 [UU 远程阻断复测](UU远程阻断复测_20261102.md)。下文保留首次本机检查时尚缺远端验证的历史范围。

## 结果

**已实际重新启动原版 UU GUI、当前用户 Service 和 Server。本机恢复检查通过：原版启动任务正常、没有项目副本或实验 Hook 映射、官方 CLI 报告已登录且网络连接正常、能够获取本机远程协助 ID、实际窗口显示远程协助页面。**

用户明确表示暂时不能配合另一台设备连接，因此本轮没有验证远端连入、画面持续更新、键鼠控制及断线重连。不能宣称“远程使用已完全恢复”。

**纠正一项此前判断：辅助功能树中的错误文案可能处于隐藏状态。** 此前根据 AX 文本推断“UU 界面仍在报 1001”并不可靠；本轮复核发现，正常协助页面的 AX 树仍返回“无法连接至服务器”和“正在连接”。实际窗口截图中没有这两个标签。后续应以可见窗口、官方诊断和远端实际连接共同验收，不能仅检索 AX 字符串。

AppleScript 的两次退出请求均返回 `-128 User canceled`，但之后检查确认旧 GUI 已实际退出，才重新启动。没有把 AppleScript 返回码当作退出成功；实际以进程检查判定。用户服务 bootout/bootstrap 均返回 0，原任务达到 running 后才继续。

本轮没有更改正式 UU 程序、签名、原始启动 plist、系统网络设置或隐私权限，也没有重新运行重签副本实验。根级 Daemon PID 3980 保持原状；本次完整重启范围是 GUI 与当前用户 Service/Server。原生考试 Demo 仍在运行，不影响上述本机检查结果。

没有通过脚本写 UU 用户配置；UU 自身在退出/启动期间更新了 `ability.config`、`pub.config`、`setting.config`，所以不能声称所有配置文件字节均未变化。`service.config`、`proxy.config`、`device.config` 保持原哈希，最终允许被控/协助开关仍开启。

## 对真实原因能得出什么

1. **历史实验确实干扰过正式启动链。** 2026-11-01 的副本 Service 替换、系统日志的 peer 拒绝和用户“无法连接”反馈都是真实证据。原恢复流程只验证了启动定义，未验证远程功能。
2. **本轮没有再观察到相同的 IPC 拒绝。** 07:07:19–07:10:00 的新进程日志中，正式 GUI 和 Server 与正式 Service 建立 peer 端点，存在证书验证成功和 HTTP 200；没有 listener reject 或 TLS 信任失败。
3. **现有证据不足以确定最初故障的唯一底层原因。** 不能把动态错误码 1001 等同于系统的 `NSURLErrorDomain -1001`，也不能仅凭重签副本就断言具体签名校验拒绝。未解码的 UU 二进制业务日志和缺少本轮远端连接对照仍是限制。
4. **本轮验证了可恢复到原版、本机功能就绪。** 它不证明所有远程功能可用，也不证明必须执行本轮全部重启步骤才能恢复。由于重启前没有可见窗口或远端连通对照，不能严格量化哪一步消除了故障。
