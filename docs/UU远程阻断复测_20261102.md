## 测试条件与动作

用户明确授权重新启用旧设置复测，并要求测试后恢复。基线连通确认已保存；没有把先前仅 CLI 正常的状态冒充远端可连接。

本轮复用了 `uu-copy-service-experiment.py`，从正式用户服务切换到 `UURemote-Test-Resigned.app` 中的 Service。与上一轮相比，副本 Service、`libCaptureHook-v1.2.dylib`、配置文件的 SHA-256 和模式都相同。

**模式仍为 `audit`。** 这是对原故障条件的复现，没有改为 `block`，也没有增加新的网络封禁规则。库仍会安装进程内 Hook，因此 `audit` 不能理解为对进程完全没有影响。

没有修改 `/Applications/UURemote.app` 的文件或签名，没有改写 `/Library` 原始启动 plist，没有修改系统网络或隐私配置，没有终止根级 Daemon。原启动 plist 哈希保持不变。

## 日志与原因判断

实验活动期的固定 21 秒窗口中，正式 Daemon PID 3980 记录了 4 次 `Peer connection was rejected by the listener (xpc_connection_cancel())`，时间紧邻针对副本 Service 26999 的 peer 事件。副本 Service 还记录 1 次同类拒绝，邻近副本 Server 27031 的连接事件。

恢复后的固定 35 秒窗口中，正式 Daemon 创建 Service 27787 的 peer，Service 创建 GUI 27790 和 Server 27803 的 peer；没有观察到同类 listener reject。该窗口还存在正常的 TLS 验证及 HTTP 200。

结合实际远端三阶段结果，证据支持：**替换为实验副本并加载该 Hook 的组合条件会干扰 UU 的内部通信，导致本轮设备离线；恢复正式组件后通信和远控恢复。**

证据尚不能进一步证明拒绝一定源于某一项签名检查，也不能分离“副本重签名”“Hook 注入”“其他副本运行差异”各自的影响。本轮没有做“同一个副本完全不加载 Hook”的独立对照。日志中的普通签名验证活动、文件缺失提示或 HTTP 400，均不能单独当成明确的鉴权失败原因。

## 恢复实现与未覆盖范围

本次新增的是**一次性实验恢复守护**，路径在本轮 artifacts 内。它监督实验子进程，接受提前恢复请求，并设置 8 分钟截止时间。恢复时验证任务身份，只处理当前用户及精确路径的相关进程，并检查：

- 原 plist 哈希和原服务路径；
- 原任务达到 `running`；
- 正式 GUI、Service、Server 均存在；
- 副本进程全部退出；
- 当前环境和库映射无实验 Hook。

本轮实际验证了请求触发恢复；**超时分支没有实际触发，考试结束/崩溃自动触发也尚未接入。** 该普通用户守护不是抗管理员篡改机制，不能保证机器断电或守护自身被强制结束后仍执行恢复。

本轮没有测试：实验期间重启 UU 是否仍阻断、系统重启后的行为、管理员绕过、其它远控工具、长时间稳定性。连接失败应记为“实验导致远控不可用”，不能记为“画面遮蔽通过”。
