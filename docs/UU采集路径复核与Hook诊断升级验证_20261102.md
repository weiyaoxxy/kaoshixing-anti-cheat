# UU 采集路径复核与 Hook 诊断升级验证

日期：2026-11-02。用户时间采用 Asia/Calcutta（UTC+05:30）。本轮实际 UU 采样在 14:53–15:25 完成，随后结束测试窗口并核对原环境。

## 结论

**本轮在正常远控的原版 UU 中重新确认了真实采集处理路径：`UURemoteServer → ScreenCaptureKit 视频接收回调 → libstreamer::ScreenCapturerSck::OnReceiveVideoSampleBuffer`。** 未连接、已连接、断开后的对照均完成；连接期间用户确认动态画面和按钮操作正常。

**这项结果来自外部运行栈观察，不是我们的 Hook 在 UU 中命中。** 同时已实现 CaptureHook v1.4 的诊断扩展并通过自有宿主验证，但尚未解决原版 UU 接受本库加载的问题，也没有验证 UU 中的画面遮蔽。没有把自有宿主帧证据与原版 UU 的采样结果拼接成注入成功。

本轮未修改、重签、重启或切换 UU；未修改 TCC、SIP、钥匙串或 launchd 配置。采样会短暂挂起/恢复线程，不能称为完全无干预；用户报告采样期间画面和操作一直正常。测试结束时 UU 保持正式进程，远端按用户操作断开。

## 2. 观察到的具体调用关系

两个 Server 样本都包含同一祖先/后代分支：

```text
ScreenCaptureKit
  [SCStream(SCContentSharing) startRemoteVideoReceiveQueue:] block callback
    ↓ 中间桥接栈帧
libstreamer.dylib
  streamer::capture::ScreenCapturerSck::OnReceiveVideoSampleBuffer
```

第一份 Server 样本对应原文行 753→754→755；第二份包含 733→734→735 以及另一条后代分支。分析没有删除桥接后宣称两者直接相邻，也没有把不同线程的符号拼接成调用链。

两个样本还分别出现 libstreamer 编码器和 `VTCompressionSessionEncodeFrame` 的编码分支；第二份还观察到同采集分支的 IOSurface 处理。编码证据来自其他队列，没有同帧标识，不能据此证明某一帧已经传输或显示。它们是辅助路径证据。

详细脱敏链：[Server 第一次](../artifacts/uu-capture-route-20261102T092238Z/connected/03-server-69791-analysis.json)、[Server 第二次](../artifacts/uu-capture-route-20261102T092238Z/connected/06-server-69791-analysis.json)。

历史材料中其实已经有同类 SCK/libstreamer 运行栈。本轮复核了旧材料摘要，并用新的真实连接/断开对照重复观察。因而应明确：**采集路径已有依据，仍未打通的是原版采集进程内的 Hook 加载与命中。**

## 3. 本轮实现的代码

### CaptureHook v1.4

- 新增 `SCShareableContent.getShareableContentExcludingDesktopWindows:onScreenWindowsOnly:completionHandler:` 的请求/结果诊断，用于观察采集准备阶段。仅记录调用关联、成功/失败、错误域/码和数量，不记录窗口标题、应用对象或画面内容。
- 新增 `CGDisplayStreamStart` / `CGDisplayStreamStop` 调用和返回值诊断，保持原参数/返回行为。该项不直接建立帧证明。

| Hook 严格分析器单测 | **63/63** | 旧证据兼容、新诊断关联、版本约束、诊断不误升采集等级 |

另用独立自有 heartbeat 进程验证 sample 收到 SIGINT 后退出、目标心跳继续和临时文件清理。最终 fixture 通过；中间一次严格用户目录路径检查失败，原因是 sample 路径匿名化，失败记录仍保留。该测试不扩展为 UU 或所有异常退出的保证。[最终 fixture 结果](../artifacts/sample-cleanup-fixture-20261102T092634Z/summary.json)

## 6. 环境核验与限制

末尾原始四组件、libstreamer 和两份启动 plist 的哈希与本轮初始清单全部一致，原应用严格递归签名校验通过。三个正式用户进程的 vmmap 均未发现本项目已知 Hook/Witness 文件名。文件名观察不能排除任意其他 Hook，也不代表内存真实性远程证明。[末尾核验](../artifacts/uu-capture-route-20261102T092238Z/final-verification.json)

原始 sample 报告只在私有临时目录内解析，未永久保存；留存其摘要、独立身份清单和最小脱敏调用链。后续可审查已保存的证据与解析器，但不能对已删除的完整原文重新解析。当前日志和清单仍是本地可修改材料。

本轮采样负例数量很少，且符号匹配针对当前版本；不能直接作为考试中的通用会话检测器。未采到也可能因为采样时机、其他后端、符号变化或覆盖不足。持续采样的性能与稳定性还没有完成产品级评估。

## 7. 下一步的明确条件

本机该版本在本次连接中观察到 Server 的 SCK 输出处理路径，不能排除其他场景或回退后端。源码已实现相关 SCStream 包装，并在自有宿主验证部分调用和回调；尚未证明这些包装在原版 UU 中加载或命中。继续增加接口数量不能解决当前加载前提。跨厂商适用范围和更完整的产品边界见[Hook 路线总审计](Hook路线完整审计与架构决策_20261102.md)。

若目标是“真实 UU 调用经过本库”，下一步仍需可正常连线且允许插桩的 Server 环境，例如厂商支持的配套测试构建或集成入口。当前没有取得新的受支持加载方法，因此本轮不重复此前导致授权/IPC 问题的副本切换，也没有把外部路径结果宣称为注入成功。

若目标转为“考试客户端发现 UU 运行并终止”，可按[进程管控设计](UU考试进程管控设计_20261102.md)独立实现；这条产品路线不依赖把 Hook 放进 UU。它与本轮采集路径验证是不同交付，不能用本报告代替强退、上报和恢复验收。
