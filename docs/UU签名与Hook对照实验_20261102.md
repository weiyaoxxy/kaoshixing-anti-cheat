# UU 重签名副本与 Hook 的对照实验

日期：2026-11-02。时间统一为 Asia/Calcutta（UTC+05:30），原始 JSON 使用 UTC。

## 结论

**已通过实际对照证明：此前 UU 无法连接，并不需要 Hook 注入也会发生。相同重签名副本去掉 Hook 后仍离线；保留原厂签名、与正式应用内容一致的副本，在不加载 Hook 时能够正常连接，画面和操作也正常。**

故障定位从“重签副本与 Hook 的组合条件”缩小到“现有重签名副本的变化”。签名检查显示：正常副本保留厂商 Team ID `PU9BNSBJW7`，失败副本为 ad-hoc 签名、Team ID 未设置。结合正式 Daemon 的重复连接拒绝，**与原版组件的身份/信任校验不兼容是当前最有力的解释，但仍属于推断，日志未直接公开具体校验规则。**

**所有实验已结束，`/Applications/UURemote.app` 的原版 GUI、用户 Service 和 Server 已恢复。用户最终确认“可以，画面和操作正常”。两个恢复守护均已退出，没有遗留实验副本或 Hook。**

## 第一组：同一重签名副本，移除注入

复用上一轮相同副本文件、服务标签、MachServices、WorkingDirectory 及参数，仅删除启动定义中的四个环境变量：`DYLD_INSERT_LIBRARIES`、`HOOK_DEMO_CONFIG`、`HOOK_DEMO_LOG`、`HOOK_DEMO_MODE`。

- 08:08:19 启用；副本 Service 37078、Server 37085，正式 GUI 27790。
- 三个进程的 `vmmap` 均返回 0，均无实验库；Service 和 Server 实际路径均为同一重签名副本。
- 08:08:19–08:08:49 固定窗口：正式 Daemon 3980 有 6 次 listener reject，副本 Service 有 1 次。
- 用户实际重连反馈“无法连接／设备离线”。
- 获得结果后立即触发恢复，08:12:45 完成正式运行检查；该守护退出后才进行第二组。

该组足以排除“只有 Hook 执行才会导致这次离线”的解释，**不能据此推断 Hook 在所有环境下都不会引发其他问题**。

## 第二组：原厂签名副本，无注入

使用 `sandbox-apps/UURemote-Test.app`。预检确认其 94 个文件/符号链接内容与当前正式应用一致，无新增、缺失或内容差异；两份应用的严格递归签名验证均通过，关键组件的 Team ID 与 CDHash 一致。

- 08:13:45 启用；副本 Service 38716、Server 38728，正式 GUI 38385。
- Service 和 Server 均实际运行于原厂签名副本，未意外复用正式 Server；三进程均无实验 Hook。
- 08:13:45–08:14:15 固定窗口没有 listener reject；Daemon、Service、GUI、Server 有对应 peer 端点。
- 用户实际反馈“能连接，画面和操作正常”。
- 随后恢复 `/Applications` 中的正式安装版，08:19:24 完成运行检查；新 Service 40404、GUI 40406、Server 40415。
- 用户最后再次确认“可以，画面和操作正常”，反馈保存于 08:21:35；该时间是记录时刻，不作为精确连接建立时刻。

## 为什么还不写成“只改签名必然失败”

本轮可以区分“现有重签名副本”与“Hook 是否加载”，但并未构造只有密码学签名字节不同的严格单变量样本：

- 现有重签名副本还调整了 entitlements，并将关键可执行文件变成 arm64 单架构。
- 两个副本的路径不同；副本与正式安装版还存在所有者和部分扩展属性差异。元数据抽样范围见预检证据。
- 各轮会使用 UU 自身的共享运行状态，不能把这些实验称作完全隔离环境。
- 系统日志只报告 listener 拒绝，没有直接给出拒绝 peer 的完整身份与具体校验条件；相邻 peer 事件提供关联证据。

因此，准确结论是：**Hook 不是复现故障的必要条件；故障与现有重签名副本的身份/权限等变化有关，保留原厂签名的副本可正常运行。** 尚不能精确归因到某条 Team ID、证书链或 entitlement 检查，也不能把它视为稳定的防作弊控制机制。

本轮没有修改正式应用、原始 `/Library` plist、系统安全设置或网络规则，没有终止根级 Daemon。原启动 plist 哈希未变。两个一次性守护均由实验结果触发提前恢复；超时分支、考试结束自动触发和管理员绕过仍未实测。
