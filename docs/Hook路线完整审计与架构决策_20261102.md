# Hook 路线完整审计与架构决策

审计日期：2026-11-02。范围：当前项目的 Hook 核心、部署与恢复、考试 Demo、完整性监测、测试工具、三家远控证据，以及受保护渲染和 AAC 替代路线。现场环境为 Apple M4 / macOS 26.6.2；历史实验的版本和时间分别保留。

## 1. 决策

**“拦截采集接口并修改输出”作为限定条件下的技术实验成立；“向任意第三方远控进程注入 Hook，作为考生拥有管理员权限时的通用防作弊主方案”不成立于当前实现和证据。应调整主路线，而不是继续以增加 Hook 数量为主要推进目标。**

这不是用三款软件算出“成功率 33%”。ToDesk 已到达远端遮蔽验证，UU 和向日葵主要停在正常业务进程的加载前提，三者不是相同条件下的随机样本。两家未加载不能证明 Hook 算法本身无效，但暴露出方案依赖厂商允许加载的结构性问题。

更强的反例已经存在：**ToDesk 遮蔽成功时，另一个未加载 Hook 的独立进程仍取得原始考试画面。** 即使补齐另外两家，也不能推出全系统防采集。原始帧还会先进入被监控进程的地址空间，本库仅替换其中一段输出，不构成对该宿主的可信隔离。

此前若将剩余问题概括为“只差加载兼容性，其他基本解决”，该概括过窄。部署、输出完整性、故障策略、考试生命周期、证据可信度是不同问题；增加接口和日志只解决其中一部分。

## 2. 审计方法与范围限制

本轮逐段审读当前 `CaptureHook.m`，核对 NativeExamDemo、RuntimeIntegrityMonitor、UUHookMonitor、三个厂商部署/恢复工具、UU 副本工具、探针和证据分析器；交叉核对原始 JSON/JSONL、人工反馈、最终报告及历史 Word 正文。另审查原受保护视频层 Demo、原生控件渲染路线和 AAC 示例的关键实现与已知反例。

本轮没有重新启动、终止或注入任何第三方远控，没有新采集真实屏幕。运行的验证仅为现有纯逻辑单测、自有合成像素测试和系统操作已替换为 mock 的恢复故障测试。

“完整审计”在此指覆盖安全相关的端到端流程和跨文档结论，不表示穷尽所有并发状态、逐帧重审全部历史视频、审计厂商闭源实现或逐行审计附带的第三方媒体工具。旧证据中的外部栈原文部分已删除，只能核对保留的脱敏解析结果、哈希和方法，不能重新独立解析全部原文。未实测的推断在下文单独标注。

证据强度必须分开：启动环境已设置 → 库实际加载 → 包装已安装 → 接口实际调用 → 有效图像经过 → 输出处理完成 → 接收端画面符合目标 → 全考试周期及异常情况下仍成立。前一层不自动证明后一层。

## 4. 关键发现

以下“阻断项”针对通用防作弊产品目标；P1 表示投入实际考试前必须解决的高优先级问题，P2 表示影响证据或复现可靠性的问题。它们不是对第三方软件的漏洞评级。

### F01：阻断项——控制位于不可信采集进程内部，且不覆盖其他进程

[CaptureHook.m](../Hook新方案_20261101/Sources/CaptureHook/CaptureHook.m) L184 先调用原始截图；L325–346 接收、复制原始样本；L378–379 再替换交给原输出的样本。此时原始像素已在宿主地址空间中。它是输出过滤，不是系统向第三方交付像素之前的授权关卡。

直接实测反例：[scope-check.json](../Hook新方案_20261101/artifacts/todesk-block-20261101T135207Z/independent-unhooked-check/scope-check.json) 中 `secretDetected=true`。已有报告也明确记录该边界，见[新方案验证报告](../Hook新方案_20261101/docs/新方案验证报告.md) L45 附近。

结论：修正所有下面的代码缺陷，也不能消除这一架构边界。不能把“指定远控输出变黑”替换为“设备上的对方无法取得题目”。

### F02：阻断项——加载资格由第三方宿主决定

本机实测 ToDesk 版本允许 DYLD 环境变量并关闭 Library Validation；UU 和向日葵受检原版组件没有这两项例外。给本库签名或给考试客户端管理员权限，不会自动改变第三方宿主的授权和签名约束。

Apple 说明强化运行时用于限制注入等行为，动态库继承宿主可执行文件的 entitlements；Library Validation 默认要求 Apple 或与主程序相同 Team ID 的代码。两家负结果与这些限制相符，但本轮没有证明 dyld 内部唯一拒绝步骤，也没有穷举所有加载技术。[Apple Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)、[Library Validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)。

结论：继续研究第三方 Hook 的入口条件应是厂商合作、受支持插件或受控测试构建。没有新的加载依据时，继续增加截图接口不会改善当前瓶颈；修改签名导致业务失效也不是可部署的防护成果。

### F03：P1——block 模式明确存在原帧放行

`CaptureHook.m` L134–152、L215 起、L325–342：目标配置不可用、未知范围、source crop、比例不支持、非 BGRA/planar、分配/锁定/样本创建失败等路径均可能原样返回。它们是兼容优先的 fail-open 设计。

本轮合成验证确认：关闭目标配置、source crop、32ARGB 输入均返回同一个原始样本对象。不是仅有风险提示，具体控制流已复现。若进入考试产品，无法确认保护应触发“不展示题目/暂停”，不能继续考试并把 block 标志当成保护已生效。只把失败分支改成黑帧也不能解决 F01、F02，并需验证宿主能否正确处理。

### F04：P1——遮罩几何模型不完整

`CaptureHook.m` L298–305 的 SCK `Scope()` 只标记 sourceRect；L143–152 按整张输出尺寸计算矩形，未处理 destinationRect 或逐帧 contentRect/contentScale/scaleFactor。

合成模型中，敏感区域应位于输出的 `(55,55,10,10)`，实际算法得到 `(8,8,24,24)`，两者不相交。**已确认算法缺口；没有据此认定任何真实远控已经发生泄漏。**

窗口移动/缩放时另行更新 JSON，而回调使用当前配置，不按帧时间绑定；流更新见 L415–416。修改像素后 SCK attachments 和 CGDisplayStream update 信息基本沿用原值，代码未主动扩展脏区以覆盖新增遮蔽区域。这可能影响增量编码/旧帧缓存，真实影响尚待验证；合成测试只确认元数据被原样保留。

### F05：P1——配置没有可信身份及新鲜度绑定，结构异常可能影响宿主

`CaptureHook.m` L114–122 读取用户目录 JSON，没有验证 ownerPID、时间戳、schemaVersion 与实际窗口身份；字段类型也未完整检查。NativeExamDemo 在 [main.swift](../Hook新方案_20261101/Sources/NativeExamDemo/main.swift) L372–380 写入该配置。

合成验证接受 ownerPID=999999、时间为 2000 年的目标；`bounds.x={}` 引发 `NSInvalidArgumentException`，生产函数无相应外围异常保护。前者可导致使用错误/陈旧目标，后者可能使注入宿主异常。当前文件通道不是对抗管理员的可信策略通道。

### F06：P1——接口与生命周期覆盖没有完备性证明

`CaptureHook.m` L266–272、L430–447 是固定 C 入口和 ObjC selector 列表。没有专门覆盖当前 SDK 的某些新截图入口、`SCRecordingOutput` 注册路径，也没有接管加载前已存在的所有流和输出。未专门覆盖不等于已证明能绕过，因为内部可能复用已有接口；正确结论是这些路径未验证。

两个探针主要使用固定 BGRA 和有限配置；[CaptureProbe.swift](../Hook新方案_20261101/Sources/CaptureProbe/CaptureProbe.swift) L178 的更新是再次提交同一个 filter，不能替代真实切屏/改变范围的回归。更多 Hook 只能扩展已加载宿主内的覆盖，不能推出完整性。

### F07：P1——Demo 尚无考试准入、异常处置和结束恢复闭环

NativeExamDemo `main.swift` L142–151 先显示原生试题，再启动完整性检查；L299–319 的异常处理更新标签和本地记录，没有暂停考试或隐藏试题；L392–397 退出仅保存状态，使配置 disabled，没有调用远控恢复控制器。

[UUHookMonitor.swift](../Hook新方案_20261101/Sources/NativeExamDemo/UUHookMonitor.swift) 的职责是尽力、只读识别已知模块名，检测不到改名模块不代表没有注入；无权读取的进程正确标为未知。RuntimeIntegrityMonitor 检查自己进程中的有限信号，不是独立于被检查进程的可信证明。

具体而言，UU 监测按四个候选可执行名称和已知库名匹配，读取的磁盘签名元数据不等于验签成功或运行代码身份证明。一次扫描预算为 9 秒，不能保证发现所有短时进程。完整性监测只检查四个 ObjC 方法等有限信号，初次本地观察提供方法基线；默认构建为 ad-hoc 签名且未启用 Hardened Runtime。`serverReported=false`、`local_only_not_remote_attestation` 是当前代码主动保留的准确边界。

[UU 考试进程管控设计](UU考试进程管控设计_20261102.md) 是设计文档：其中的生产 root helper、服务端回执、连续考试策略和 ES 没有在当前 Demo 中组成可运行系统；AAC 另有未接入 Demo 的示例。现有本地 JSON/JSONL 可以帮助复核，不能承诺最高权限对手绕过后必有不可删除记录。后台自动重启也不等同于考生主动作弊。

### F08：P1——部分恢复流程会被日志写入失败阻断

[todesk-proxy-instrument.py](../Hook新方案_20261101/scripts/todesk-proxy-instrument.py) 和 [uu-service-instrument.py](../Hook新方案_20261101/scripts/uu-service-instrument.py) L300–304 在启动失败处理里先 `save(state)`、后进入恢复；L198 的恢复入口也依赖事件写盘。若磁盘已持续写失败，恢复可能根本没有执行。

本轮两个纯 mock 用例均复现“原任务 bootout 后模拟写盘失败，restore_attempts=0”。没有执行真实 launchctl，不能描述成这次真实机器恢复失败。[复现源码与结果](../artifacts/hook-route-audit-20261102/deployment/README.md)。UU 副本工具 L340–344 有同类控制流，为静态确认，未计入上述两个动态复现。

旧 ToDesk/UU 启动器成功后退出，没有独立截止租约；切换 launchd 任务也不保证所有已经派生的 Session/Server 都退出。向日葵的新实验控制器已有截止恢复和隔离日志错误等改进，本轮 13 项 mock 回归通过，但普通 Python finally 仍不能承诺 SIGKILL、断电后的恢复。这些实验恢复机制也尚未接入考试结束。

### F09：P2——成功日志存在错误路径，且抽样不能证明全帧安全

`CaptureHook.m` L164–166 在 `CGBitmapContextCreateImage` 返回 NULL 时仍写 `image_redacted`，随后返回原图。本轮在自有合成编译单元中仅将该函数替换为返回 NULL，复现了“返回原图与成功日志同时出现”。这不表示历史远控测试发生过此故障，但说明日志不能独立验收遮蔽。

流日志仅记录首帧、每 60 帧等样本；分析器支持预期结束序号，但若没有独立取得的结束序号，删除完整尾部记录无法仅凭现有日志发现。分析器正确保留 `logAuthenticityVerified=false` 和 `captureBlockingVerified=false`。63 项分析器测试通过，证明合成事件关联和分级，不证明远端画面或日志不可伪造。

### F10：P2——源码版本、历史二进制和文档入口有错位

[build-hook.sh](../Hook新方案_20261101/scripts/build-hook.sh) L5 默认构建 v1.4，并拒绝覆盖已有文件；[democtl.py](../Hook新方案_20261101/scripts/democtl.py) L61 固定加载 `build/libCaptureHook.dylib`，本机这个文件仍是历史 v1.2。代码包不含二进制时，直接照旧 README 构建也不会生成该旧别名。

因此“重新构建后点 ToDesk 按钮”并不等于测试当前源码。后续若继续研发，应显式指定并记录库路径/哈希，绑定源码和验收结果；不可覆盖历史 v1.2 或把 v1.4 冒充原验收版本。

本轮已修正文档入口：区分原渲染 Demo 与 Hook Demo、补齐三家最新报告、说明跨目录证据和保留的 UU 应用副本；收窄 UU 报告中“接口已覆盖”的表达。历史 Word 和旧实验正文保留原日期及结论。本轮未修改 Hook 或恢复工具的行为，上述代码缺陷仍是待修项。

## 6. 推荐的产品方向

先将三个不同目标写清楚：

| 目标 | 主要机制 | 当前状态与边界 |
|---|---|---|
| 考试期间禁止不允许的远控程序运行 | 考试准入检查、已验证进程身份、受控服务、异常暂停和服务端策略；需要执行前拒绝时评估 ES | 当前主要是设计；普通轮询后 kill 是事后处置，有窗口，不等于执行前禁止 |
| 题目画面不交给普通外部捕获 | OS 支持的考试限制；或在自有应用内重构受保护渲染 | AAC 尚未授权实测；渲染 PoC 有局部正结果，也有已知输入法等泄露 |
| 记录被绕过/状态异常 | 独立服务端回执、序列、策略版本、缺失区间和人工复核 | 服务端能证明收到/未收到什么，不能仅凭普通客户端自报证明最高权限设备上没有作弊 |

### 首选：围绕 OS 支持的考试会话设计，Hook 降为辅助实验

AAC 的约束在操作系统层实施，不需要逐一修改远控宿主。Apple 列出的 macOS 考试限制包括屏幕共享、屏幕捕获和 Remote Login；需要批准的考试应用能力。支持 AAC 的应用并不一律要求 MDM，设备管理是另一个可选控制条件。[Apple 考试模式说明](https://support.apple.com/en-us/101976)。

这是一条更匹配目标的候选主线，**不是项目已经验证可用的替代品**。当前只有 [AssessmentSessionExample.swift.txt](../Sources/AssessmentSessionExample.swift.txt) 示例，刻意未加入可运行 Demo；L10–12、L74–75 已注明保护成功前不展示题目、与自有原始帧录像的兼容性尚待实验。

申请和实测的重点应是：会话成功才发题；失败/中断立即隐藏并暂停；退出恢复；真实第三方远控、输入、辅助功能和自身录像组合是否满足需求。不能把“Apple 有考试模式”写成三家软件所有版本均已通过验收。

### 过渡方案：进程管控可以先做，但明确接受范围

若短期需求只是降低常见远控风险，可按现有进程管控设计实现最小闭环：展示题目前建立监测并清理已确认的远控组件；考试中发现启动时记录身份/时间、隐藏题目、处置后复查；上报服务端并等待策略决定；正常结束和异常退出均有可恢复租约。

后台 KeepAlive 重启、用户误开、主动对抗应分级记录，不直接把任何进程出现判成作弊。普通管理员 helper 的可用性与完整性要单独监测；若考生能够控制整个系统信任环境，不能保证本地检测必然留下可信证据。

要在执行前拒绝指定程序，评估 ES 的 AUTH_EXEC，而非加快轮询。ES 需要专用 entitlement 等条件，不能替代已经运行会话的清理，也不是按窗口过滤图像的接口。Apple 还说明 ES 作为系统扩展有强于普通 daemon 的保护；不能把“普通 root helper 可被 root 停止”错误外推成“所有 ES 系统扩展也一样”。[Apple ES 机制与部署](https://developer.apple.com/videos/play/wwdc2020/10159/)。

### 画面保护补充：受保护渲染值得保留，不能直接宣布替代成功

原始 Demo 把自有帧送入 `AVSampleBufferDisplayLayer.preventsCapture`，再从同一源帧独立写录像。保护对象是该 Layer，不是任意已有原生窗口；也不是赋予自己系统录屏白名单。[Apple preventsCapture](https://developer.apple.com/documentation/avfoundation/avsamplebufferdisplaylayer/preventscapture)。

项目[原生控件验证报告](../原生控件验证_20261101/docs/原生控件验证报告.md)已给出边界：需要把控件画面栅格化并代理输入；系统中文候选条仍可被截图；曾显示后隐藏的源窗口内容曾被捕获；AX 和所有系统辅助 UI 没有完整保护证明。应先解决这些已知反例，再谈支持完整题型及输入体验。也不能将这条路线的自身录像结果迁移到当前普通原生 Hook Demo。

源码还保留了仅适用于合成实验的通道：[原生控件 main.swift](../原生控件验证_20261101/Sources/NativeControlDemo/main.swift) L55 转发剪贴板操作，L237–265 保存原始 PNG 和输入文本，L280–292 接受本地 `control-command.json` 来保存原图或显示源窗口，未认证命令发送者。根画布 Demo 也默认保存明文参考 PNG 和普通 MP4。这些有助于验证，但必须从生产构建移除或重新设计，不能把试验 Demo 当作已加固客户端。受保护 Layer 本身也不承诺保护这些明文文件。

深度调研中的 Clear Key 是播放器媒体链实验，`allowsCaptureOfClearKeyVideo` 作用于对应播放器内容，不是普通原生窗口保护开关；同进程 VideoOutput 曾取得明文输出。该方案还需要实时 UI 媒体化、交互延迟和独立捕获验证，不能直接顶替现有考试界面。参见[深度复核报告](../深度调研_20261101/docs/深度复核与审阅问题.md)。

## 7. 后续验收门槛与停止条件

1. **先定威胁模型。** 可接受的目标是阻止约定环境中的常见违规远控，还是对抗能够控制系统信任环境的设备所有者。后一种要求不能仅由当前普通本地进程和本地日志保证；需要 OS 支持的约束、受控设备条件或调整承诺。
2. **先做考试生命周期，再谈软件清单。** 准备→确认保护/监测有效→展示题目→异常隐藏暂停→恢复复查→结束释放。验收要覆盖启动失败、进程重启、权限缺失、日志写失败、客户端崩溃、网络中断和服务端未收到状态。
3. **真实远控验收必须有动态对照和独立证据。** 固定系统/软件/库版本及哈希，记录实际负责采集的 PID；证明有效帧、接收端连续动态画面、考试区域行为、异常提示和恢复。黑屏、冻结、离线、无帧必须独立判定，不能统一算“防护成功”。
4. **继续 Hook 的前提是新的可行加载条件。** 若有厂商允许的加载入口，再修复 F03–F10，并做格式/裁剪/缩放/切屏/多输出/重连/缓存/故障等验证。没有此条件，暂停对原版 UU、向日葵反复重签或新增接口的实验；现有采集器和分析器仍可用于定位路径与回归。
5. **成功标准绑定安全目标。** “记录到一条 API 调用”是诊断成功；“本次接收端考试区域不可见”是有限效果成功；“全考试期间、在约定对抗条件下无法取得题目”是更高层的产品验收，不能用前两者代替。

最终建议：保留 ToDesk 的有限正结果和现有诊断工具；正式降低第三方进程注入 Hook 的主方案地位；将下一阶段资源投入考试会话/进程策略/异常暂停/恢复/服务端证据闭环，并对受保护渲染已有泄露做定向验证。即使最终不使用 Hook，这轮实验也已经给出足够明确的路线取舍依据。
